# 节点终端镜像按节点架构选 `-arm64`

日期：2026-11-07
状态：已实现

## 1. 背景与结论

节点终端的 Agent Pod 用 `Spec.NodeName` 直接绑到用户点开的这台节点上
（`pkg/terminal/node_terminal_handler.go`），但镜像名只有一个全局值：
`general_settings.node_terminal_image`，空则回落 `common.NodeTerminalImage`
（默认 `swr.cn-south-1.myhuaweicloud.com/gzwxh/busybox:latest`）。

公司 SWR 里 `gzwxh/busybox` 的 `latest` / `1.36` / `1.37` 都是**单架构 amd64** manifest
（不是 manifest list），所以 arm64 节点上开节点终端必定 `exec format error`；混合架构集群
里改设置也没用——同一个镜像名不可能同时满足两种架构。

结论：把「按节点架构挑镜像」这件事放进代码，沿用 SWR 既有的 `-arm64` 后缀独立 tag 口径
（同 `openeuler:24.03-lts-sp4-arm64`、`aerolink:v1.0.2-arm64`）。SWR 对 manifest list 的
解析不可靠，也不支持同 tag 多架构，所以不做多架构 tag。不加库列、不加环境变量、不加界面
开关。

arm64 那份落在 `gzwxh/busybox:latest-arm64`（单架构 `linux/arm64`，manifest
`sha256:f0836b5c…`）。它的来历有两步值得记着，否则下次补镜像会重踩（原因见 §4.2）：

1. 先用 `skopeo copy --format v2s2 --remove-signatures --override-arch arm64
   docker://docker.m.daocloud.io/library/busybox:latest` 转推一份纯净的 arm64 镜像；
2. 再用 `docker build --platform linux/arm64 --provenance=false --sbom=false` 给它加一个
   `LABEL cc.aerolink.node-terminal=arm64` 重造。第 2 步不为那个 label，而是为了让它
   **有自己的 image ID**。

## 2. 改写规则

架构取值优先级：`Status.NodeInfo.Architecture` → 节点标签 `kubernetes.io/arch` →
`beta.kubernetes.io/arch`；都拿不到就当作非 arm64，行为与改动前一致。

只有「显式带 tag、不是 digest 引用、tag 还没带 `-arm64` 后缀」三条都满足才改写，
其余原样返回：

| 输入（arm64 节点） | 结果 | 理由 |
| --- | --- | --- |
| `swr…/busybox:latest` | `swr…/busybox:latest-arm64` | 常规情形 |
| `reg:5000/team/busybox:1.2` | `reg:5000/team/busybox:1.2-arm64` | tag 分隔符只认最后一个 `/` 之后的冒号，端口号不受影响 |
| `busybox` | 不变 | 不带 tag 的名字多指向上游多架构镜像，加后缀反而把能跑的改坏 |
| `repo/busybox@sha256:…` | 不变 | digest 已锁死架构 |
| `swr…/busybox:latest-arm64` | 不变 | 幂等，不叠第二层后缀 |
| 任何值（amd64 / 架构未知） | 不变 | 只处理 arm64 |

改写落空的最坏结果是 `ImagePullBackoff`；arm64 节点上用 amd64 镜像原本是必定起不来的，
所以没有先去做仓库探测（后端也没有访问私有仓库的凭据口径）。真遇到「arm64 镜像不带
`-arm64` 后缀」的集群，把完整镜像名直接填进界面即可；若成规模出现，再补显式配置项。

## 4. 验证

### 4.1 仓库与镜像

```bash
go test ./pkg/terminal/ -run 'TestNodeArchitecture|TestApplyNodeArchImage' -v   # 全过
go build ./...
```

镜像侧（Kylin V10 aarch64 docker 机）：`docker run --rm --entrypoint uname
swr.cn-south-1.myhuaweicloud.com/gzwxh/busybox:latest-arm64 -m` = `aarch64`，并确认层内
`/bin/sh`、`/bin/chroot`、`/bin/nsenter` 齐备——终端命令是
`chroot /host || (exec /bin/zsh || exec /bin/bash || exec /bin/sh)`。

### 4.2 真实 arm64 集群上踩到的两件事

集群：6 节点 Kylin V10 aarch64 / k8s v1.32.13 / containerd 1.7.36，`nodeInfo.architecture`
与 `kubernetes.io/arch`、`beta.kubernetes.io/arch` 三个口径全部是 `arm64`——§2 的取值优先级
因此逐条对上。

**一、节点拉不到 SWR。** 事件里是
`dial tcp: lookup swr.cn-south-1.myhuaweicloud.com on [::1]:53: read: connection refused`，
即节点的 DNS 指向本机 stub 而且 stub 没起。要么修 DNS，要么离线导入：

```bash
# 开发机：导出成 docker-archive（RepoTag 就是仓库里的全名）
skopeo copy --format v2s2 --remove-signatures --override-arch arm64 \
  docker://swr…/busybox:latest-arm64 \
  docker-archive:busybox-latest-arm64.tar:swr…/busybox:latest-arm64
scp busybox-latest-arm64.tar root@<master>:/root/offline-images/
# master 上逐个节点（master 到各节点免密）
scp /root/offline-images/busybox-latest-arm64.tar root@$ip:/root/
ssh root@$ip 'ctr -n k8s.io images import /root/busybox-latest-arm64.tar'
#             ^^ -n 是 ctr 的全局参数，必须写在 images 之前，否则 flag provided but not defined
```

**二、与历史脏记录共用 image ID 会让 CRI 报错。** 把纯净的 arm64 busybox 导入后，
`ctr -n k8s.io run` 直接跑是成功的（`aarch64`），但经 kubelet 起容器就报
`failed to get image from containerd "sha256:d2482869…": image "docker.io/library/busybox:1.35":
not found` → `CreateContainerError`。原因是节点上 `docker.io/library/busybox:1.35`、
`swr…/busybox:latest` 与这份 arm64 镜像**共用同一个 image ID**（历史上被手工 retag 过），
CRI 按 ID 反查时挑中了那条已经失效的记录。换句话说：**这个集群里用默认值
`busybox:latest` 的节点终端此刻本来就是坏的**，不是「凑巧能用」。
不能靠删旧记录解决——`latest` 是具名 tag，删了之后节点又拉不到 SWR，会把「至少还有记录」
变成「彻底没有」。做法是给 arm64 那份换一个**自己的 image ID**（§1 的第 2 步），三条记录互不干扰。

顺带一个坑：`docker build` 默认附 provenance 证明，推上去的 tag 会变成「arm64 + unknown」**两条目
的 index**（`skopeo inspect` 直接报 `no image found in image index`）。走独立 tag 口径必须带
`--provenance=false --sbom=false`。

### 4.3 端到端结果

用与 Agent Pod 完全相同的形状（`privileged` + hostPath `/` 挂到 `/host` +
`imagePullPolicy: IfNotPresent` + `command: chroot /host /bin/uname -m`）在四个 arm64 节点实跑：

| 节点 | phase | 输出 |
| --- | --- | --- |
| k8s-node1 / k8s-node2 / k8s-node4 / xc-llwl.novalocal | Succeeded | `aarch64` |

测试 Pod 与各节点的 tar 副本已清理，master 保留 `/root/offline-images/busybox-latest-arm64.tar`
供以后加节点。

### 4.4 应用层端到端（已跑通）

光看 Pod 形状还不够，得确认应用真的把 `-arm64` 写进去。用同一份 `v1.0.3-arm64` 镜像在这个
集群里起了一个一次性 aerolink（`inCluster` 自集群 + 一次性超管），登录后用最小 WS 握手
`GET /api/v1/node-terminal/k8s-node4/ws` 开了一路节点终端：

```
Agent Pod: aerolink-node-terminal-agent-k8s-node4-kphpd
image=swr…/busybox:latest-arm64  node=k8s-node4      # 界面里配的仍是 …busybox:latest
Running true
WS: 101 Switching Protocols → "waiting for pod …" → "." → "ready!" → "Terminal connected successfully"
```

两点环境口径值得记下：

- **节点终端路由前缀是 `/api/v1`**（`registerClusterProtectedRoutes` 挂在 `defaultAPI` 与
  `/api/v1/_clusters/:cluster` 两个组下）；少写一层就是 404，容易误判成「功能没生效」。
- **master 上 `ctr`/`crictl` 能看见导入的镜像，kubelet 却报 `ErrImageNeverPull`**（与 kubelet
  的运行时端点排查无关，两边 socket 是同一个文件）。同类情况不要跟 master 较劲，把待验的 Pod
  调到 worker 节点上即可（worker 节点上 IfNotPresent + 导入镜像是正常的）。

一次性部署件（Pod / ConfigMap / SA / ClusterRoleBinding / 脚本与 cookie 文件）已全部删除，
集群 6/6 Ready、`default` 与 `kube-system` 无遗留 Pod。

## 5. 不在本次范围

- `KUBECTL_TERMINAL_IMAGE`：kubectl Agent 不绑节点（无 `NodeName`/`nodeSelector`），
  纯 ARM 集群里同样可能被调度到 arm64 节点而失败，但那是另一个镜像与另一条路径。
- Pod 调试容器默认镜像 `busybox:1.37`（`ui/src/components/pod-debug-dialog.tsx`）仍是
  amd64；需要时按同一口径补 `1.37-arm64`，界面里也可手工填写 arm64 镜像名。
- 其它架构（`s390x`、`mips64le` 等）不做后缀改写，内网没有这类节点。
