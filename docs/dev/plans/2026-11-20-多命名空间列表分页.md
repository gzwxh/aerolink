# 多命名空间列表的分页语义（v1.0.4）

日期：2026-11-20
状态：已实施

## 问题

列表页多选命名空间时，前端把选择折叠成 `_all` 请求（`use-resource-table-state`），
服务端返回的是**整个集群**的一页数据，再由 `ResourceTable` 在客户端按选中集合过滤。

这带来两个不可修复的组合缺陷：

1. **分页窗口错位**：服务端 `limit` 发生在任何过滤之前。选中的命名空间若排在
   全集群列表靠后的位置（实测：`swy-base/swy-congo/swy-open` 的 19 个 Deployment
   在 1246 条里排第 922 位），前 200 条里一条也不属于选中集合。前端
   `fetchBatch` 以「凑够 200 条」为停止条件，第 1 页就停止翻页，客户端过滤后
   永远是空表，同时响应里的 `continue` 让界面一直显示「已加载 0 行（还有更多）」。
2. **RBAC 与 `limit` 顺序**：逐条 RBAC 过滤同样发生在 `limit` 之后，权限很窄的
   账号即使翻页，也可能连续多页被滤空（`use-paged-resources` 里已有注释与兜底）。

该问题与账号权限无关：管理员在多选同一批命名空间时表现完全一致。

## 方案

把「命名空间集合」作为**服务端查询条件**，由服务端完成过滤 + 多页合并，
前端只透传集合，不再依赖「拉一页再客户端过滤」。

### 接口

`GET /api/v1/_clusters/<cluster>/<resource>/_all?limit=200&paginate=true&namespaces=a,b,c`

- 新增可选参数 `namespaces`（逗号分隔，去空、去重，上限 200 个）。
- 仅在请求为**跨命名空间**（`namespace` 为空或 `_all`）且资源为命名空间级时生效；
  集群级资源与单命名空间请求忽略该参数，行为完全不变。
- 不传该参数时，行为与之前完全一致（旧前端、AI 工具、脚本调用方不受影响）。

### 服务端行为

1. 强制走直连 apiserver（`DirectClient`）：集合过滤需要真分页，informer 缓存的
   假 `continue` token 不可用。没有 `DirectClient` 时退化为原有单页行为。
2. 循环 List：保留 label/field selector，用 `limit` + 真实 `continue` 翻页，
   对每页条目按「命名空间集合 + RBAC」过滤后累加，凑够 `limit` 条、翻到末尾、
   或达到 50 页扫描上限时停止。
3. 返回合并后的条目（按创建时间倒序，与既有口径一致）+ **最后一条真实
   `continue` token**：已经消费过的条目不会重复返回，未翻完的部分交给前端的
   「加载更多」继续。
4. 安全边界不变：`namespaces` 只做**收窄**，逐条 `rbac.CanAccess` 仍然执行；
   中间件对 `_all` 的 `HasResourcePermission` 门禁不变。

### 为什么不是「逐个命名空间 List 再拼 continue」

逐 namespace List 需要把 N 个 apiserver token 编码进一个复合 token，且跨 namespace
的创建时间排序只有两条路：页内不严格有序，或把溢出条目缓存进 token。前者改变
列表排序语义，后者让 token 体积和数据强耦合。当前实现选择「全集群翻页 + 集合
过滤 + 服务端合并」，token 语义与 apiserver 完全一致，无数据丢失/重复风险；
选中集合很靠后时最多扫 50 页，可在上限内被「加载更多」继续推进。

## 前端改动

- `fetchResources` / `useResources` / `usePagedResources` / `useResourceTableData`
  增加 `namespaces?: string[]`，多选时附加到查询串。
- `ResourceTable` 多选时传 `selectedNamespaces`；撤销上一版「多选禁用服务端分页」
  的临时兜底，恢复统一分页路径。
- 客户端 `namespaceFilteredData` 过滤保留（现在等价于 no-op），作为契约防线。
