# 方案：节点失联与数据陈旧提示（详情页刷新 / 失联判定 / 后端陈旧信号）

- 状态：**方案（待实现）**
- 触发：2026-10-16 开发集群 `dev` 的 `k8s-node101` 掉线，前端节点详情页仍显示「就绪」：
  「101 服务器已经故障了，但是当前项目的前端显示还是正常的」。

## 0. 现场还原（结论依据）

只读直连该集群 apiserver 核对（本地时间）：

| 时间 | `k8s-node101` 事件 |
| --- | --- |
| 15:27–15:52 | kubelet `FreeDiskSpaceFailed` 每 5 分钟一条（镜像 GC `Wanted to free ~180GB, freed 0 bytes`） |
| 15:56:40 | `NodeNotReady`（节点掉线） |
| 16:02:29 | `RegisteredNode`（**截图里那条事件**） |
| 16:03:18 | kubelet 重启：`Starting kubelet` / `NodeHasNoDiskPressure` / `InvalidDiskCapacity: invalid capacity 0 on image filesystem` |
| 16:08 起 | `FreeDiskSpaceFailed` + `ImageGCFailed` 持续 |

两个必须分开治的事实：

1. **截图那屏是定格快照**：`DiskPressure=True` 与 `node.kubernetes.io/disk-pressure` 污点在
   16:03:18 已被 kubelet 清掉，截图却同时显示二者 ⇒ 数据停在 16:03:18 之前，之后没再取过。
2. **现在刷新也还是「正常」**：节点对外确实 `Ready=True`、无压力污点。磁盘仍满、镜像 GC 一直失败，
   但 kubelet 重启后读不到镜像盘容量（`invalid capacity 0`），压力判定失效。这层失真不是前端能修的，
   但前端必须让「这份数据本身可能是旧的」可见。

## 1. 三个独立缺口

**A 详情页定格**：`ui/src/pages/node-detail.tsx:113` 的 `useResource('nodes', name)` 未传
`refreshInterval`，而 `useResource` 默认不自动刷新（`ui/src/lib/api/core.ts:1220`）；同页的
Pods（`:120`）与事件（`:595`）同样不刷。对比列表页默认 5s 轮询
（`ui/src/hooks/use-resource-table-state.ts:110`）。工作负载详情页的自动刷新是页面内 state 自动驱动
（`ui/src/pages/deployment-detail.tsx:101,250-264`，滚动更新 1s、稳定归 0），**没有用户可控的间隔**；
唯一带 `Off/1s/5s/10s/30s` 下拉的是列表工具栏里的硬编码 `Select`
（`ui/src/components/resource-table-toolbar.tsx:144-162`，值写死、无 i18n）。

**B 失联/陈旧不可见**：判定散在三处——详情页只看 `Ready === 'True'`
（`node-detail.tsx:613-615`）、列表页口径最全（`ui/src/pages/node-list-page.tsx:38-81`）、
图标只做映射（`ui/src/components/node-status-icon.tsx:9-53`）；`ui/src/lib/k8s.ts` 没有 node 共用判定
（只有 `getPodStatus`），全仓库没有 `lastHeartbeatTime` / `unreachable` 的引用。于是
`Ready=Unknown`（node-controller 失联时正是写这个）被显示成普通的「未就绪」；
`node.kubernetes.io/unreachable|not-ready` 被列表页的系统污点过滤器一起隐藏
（`node-list-page.tsx:141,153-155` 的 `key.includes('kubernetes.io')`）。

**C 后端静默返回缓存旧值**：默认启用 informer 缓存（`pkg/kube/client.go:187`，`DISABLE_CACHE` 才直连），
集群不可达时 `Get/List` 仍返回 200 + 旧内容；`pkg/kube/client.go:207-208` 把
`DefaultWatchErrorHandler` 注册成空函数，watch 断连不记日志、不上报。前端唯一的全局横幅只认
「后端自己不可用」（`ui/src/lib/service-status.ts`，由 `ui/src/lib/api-client.ts:210-228` 的 5xx 驱动）。
这次挂的是 worker、apiserver 还活着所以缓存跟得上；**若挂的是 apiserver/VIP，界面会永久停在宕机那刻**。

## 2. 目标与非目标

目标：① 节点详情页默认自动刷新（可关），节点/Pods/事件一起刷；② 失联、心跳停止、数据陈旧在列表页与
详情页可见，判定口径只留一处；③ 缓存数据陈旧时界面明确提示「可能已过期」，且 watch 断连留下日志。

非目标：不判定「机器是否真的可用」；不改 `DISABLE_CACHE` 语义、不加直连兜底；不动集群/命名空间作用域、
`_all` 与既有鉴权、RBAC 路径。

## 3. A：节点详情页自动刷新

- 新增 `ui/src/components/refresh-interval-select.tsx`：`{ value: number; onChange: (v: number) => void }`，
  选项沿用既有口径 `0/1000/5000/10000/30000`，文案走 i18n；`resource-table-toolbar.tsx:144-162`
  一并换成它（行为不变），消灭第二份硬编码。
- `node-detail.tsx`：`const [refreshInterval, setRefreshInterval] = useState(5000)`（与列表页一致），
  同时传给节点本体（`:113`）、Pods（`:120`）、事件（`:595`）；控件放在标题/操作区与「刷新」按钮同行。
  `useResourcesEvents` 已支持 `refreshInterval`（`core.ts:719`），数据层不用改。
- 不复刻工作负载详情页那种隐式「不稳定时 1s」逻辑：节点状态不需要秒级跟随，显式间隔更可预期，
  也不与外壳刷新按钮（`PageRefreshProvider`）冲突。
- 验证：`refresh-interval-select` 单测 + `tsc --noEmit`；手工 `cordon` 节点后不点任何按钮，
  5s 内状态卡片与列表同步变化。

## 4. B：失联与数据陈旧判定

在 `ui/src/lib/k8s.ts` 新增（与 `getPodStatus` 并列）：

```ts
export const NODE_HEARTBEAT_STALE_MS = 60_000 // kubelet 上报 10s + node-monitor-grace-period 40s 的余量
export type NodeStatusKind = 'Ready' | 'NotReady' | 'Unknown' | 'Unreachable' | 'SchedulingDisabled' | 'Pressure'
export type NodeStatus = {
  kind: NodeStatusKind
  ready: 'True' | 'False' | 'Unknown'
  unreachable: boolean      // Ready=Unknown 或存在 unreachable / not-ready 污点
  heartbeatStale: boolean   // now - lastHeartbeatTime > 阈值
  heartbeatAgeMs: number | null
  pressures: string[]       // DiskPressure 等为 True 的条件
  cordoned: boolean
}
export function getNodeStatus(node: Node, now?: number): NodeStatus
```

判定优先级与展示：

| 场景 | `kind` | 界面 |
| --- | --- | --- |
| `Ready=Unknown` 或带 unreachable/not-ready 污点 | `Unreachable` | 「失联」（destructive） |
| `Ready=False` | `NotReady` | 「未就绪」（destructive） |
| `Ready=True` 且心跳超 60s | `Ready` + `heartbeatStale` | 「就绪」+ warning「心跳已停 X 分钟，数据可能已过期」 |
| `Ready=True` 且 `unschedulable` | `SchedulingDisabled` | 「已停止调度」 |
| 其余 | `Ready` | 「就绪」 |

取舍：`Unknown` 与 `NotReady` 分开（前者是控制面收不到心跳，后者是节点自报异常，处置不同）；
心跳陈旧只在 `Ready=True` 时额外提示，这正是「缓存旧值 / kubelet 失联」的可见信号；阈值是常量
（可调会让口径不可复现）；压力不参与 `kind`，单独输出 `pressures`，避免像现在列表页那样丢掉
「未就绪 + 压力」的组合信息。

落地：`node-detail.tsx:637-697` 状态卡片与 `node-list-page.tsx:38-81` 改用同一函数（删掉列表页本地版），
`node-list-page.tsx:400-419` 状态列与 `node-status-icon.tsx` 增 `Unreachable` 类型（语义 token）；
`node-list-page.tsx:141` 的系统污点过滤改成显式白名单：保留 `unreachable`/`not-ready`/各 pressure，
其余 `node.kubernetes.io/*`、`node.role*` 仍隐藏（若实现时评审觉得 `not-ready` 与 `unreachable`
同时出现噪音大，可只留 `unreachable` + pressure，并把取舍写进注释）。

i18n：`ui/src/i18n/locales/zh.json` 增 `nodes.status.{unknown,unreachable,notReady,pressure}`、
`nodes.heartbeatStale`（含 `{{minutes}}`）、`refreshInterval.{label,off,...}`；`en.json` 可选。

测试：`ui/src/lib/k8s.test.ts` 覆盖 5 类场景（含心跳超阈值、unreachable 污点、`lastHeartbeatTime` 缺失）；
渲染断言只测「失联」徽章这条关键路径（列表页目前没有测试文件，引入成本高时以判定单测覆盖）。

## 5. C：后端把「数据可能陈旧」传出来

**5.1 客户端健康跟踪**：新增 `pkg/kube/health.go`，`K8sClient` 增 `health` 字段（`NewClient` 内构造）：

```go
func (h *Health) RecordWatchError(err error)                 // ListAndWatch 断连
func (h *Health) RecordProbeOK(now time.Time)                // 探活成功
func (h *Health) RecordProbeError(err error, now time.Time)   // 探活失败
func (h *Health) Snapshot(now time.Time, staleAfter time.Duration) ClusterHealth
```

`NewClient`（`pkg/kube/client.go:207-208`）把空的错误处理器换成记录 + 限频 `klog.Warningf`
（首次 + 每 5 分钟一条），修复「watch 断了不记日志」。注意该回调**只在出错时**触发
（`vendor/k8s.io/client-go/tools/cache/reflector.go:190-212` 没有恢复回调），
所以恢复判定必须靠主动探活。

**5.2 探活与阈值**：在 `pkg/cluster.ClusterManager` 的 1 分钟 ticker 循环
（`cluster_manager.go:530-547`）旁另起 goroutine，对每个已建 ClientSet 调
`Discovery().ServerVersion()`（3s 超时），默认 15s 一轮；同时复用 `shouldUpdateCluster` 已有的
`ServerVersion()` 结果（`cluster_manager.go:461`）避免重复探测。陈旧判定：
`now - lastAPIOK >` 阈值（默认 45s，3× 间隔）或探活连续失败，`lastAPIOK` 为零按陈旧处理。

**5.3 出口一（集群列表）**：`pkg/common/types.go:52` 的 `ClusterInfo` 增
`Stale bool` / `StaleSince string`（最后成功交互时间）/ `StaleReason string`（`unreachable`|`watch-error`），
`GetClusters`（`pkg/cluster/cluster_handler.go:45`）为已连通集群填充（现在只有 `error` 覆盖
「客户端建不起来」）。前端 `Cluster`（`ui/src/types/api.ts:656`）加可选字段，
`cluster-selector.tsx:120-152` 在 `stale` 时给提示但**不禁用**该选项（数据可能旧，不代表不能切）。

**5.4 出口二（响应头）**：`pkg/middleware/cluster.go` 的 `ClusterMiddleware` 在 `c.Next()` 前写入
`X-Cluster-Data-Stale: 1`（仅陈旧时）与 `X-Cluster-Data-Age: <秒>`。只加头不改响应体，k8s 对象仍原样
透传；`pkg/middleware/cors.go` 目前没有 `Access-Control-Expose-Headers`（只有 Allow-*，
`:52-58`），需新增并列出这两个头，否则跨源调试时 JS 读不到（生产同源无影响）。

**5.5 前端消费**：`ui/src/lib/api-client.ts` 的 `fetchReportingStatus`（`:210-228`）在拿到 `response` 后
读这两个头，交给新增的 `ui/src/lib/cluster-data-staleness.ts`（模块级 store，仿 `lib/service-status.ts`

集群列表的 `stale` 作兜底，避免页面不发请求时看不到提示。

**5.6 配置与 Helm**：新增 `AEROLINK_CLUSTER_PROBE_INTERVAL`（秒，默认 15，0 关闭）、

## 7. 风险与取舍

- 探活是唯一的「恢复」判据：阈值调大则提示滞后，调小则抖动；默认 45s 是 3× 探活间隔，
  漏报窗口 ≤ 45s，比现在的「永久无感」是净收益。
- 响应头是「本页数据可能旧」的近似信号：它反映客户端最近一次请求时的后端状态，不做逐对象的新鲜度
  证明（逐对象需要给 k8s 对象包一层信封，破坏透传，明确不做）。
- 心跳阈值 60s 依赖 kubelet 正常上报节奏；节点刚加入、时钟漂移等场景可能瞬时误报，
  因此它只作为**附加提示**，不改变就绪判定本身。
- 列表页恢复展示失联/压力污点会让污点列更长（原来被整类隐藏），属信息量与简洁性的取舍，
  方案选择偏信息量。

## 8. 顺带记录（不在本方案范围）

`k8s-node101` 的磁盘问题仍在（镜像 GC 持续失败、eviction 已触发 200+ 次），
kubelet 因 `invalid capacity 0 on image filesystem` 无法评估镜像盘压力而报 `DiskPressure=False`，
建议清镜像盘或扩容；这类「平台侧失真」需要单独的巡检项（如 kubelet 日志里的 `InvalidDiskCapacity`）
才能被平台感知，暂不在本方案处理。

## 9. 落地记录（实现偏差与取舍）

A 按方案实现，未偏离；B 有两处与 §4 不同的有意取舍，见第 4 点；C 有三处与正文写法不同的地方，都在本节说明：

1. **「不带该头即自动清除」改成了「两个头都不带时不动状态」**（§5.5）。只有集群作用域路由会带这两个头：
   `/_clusters/:cluster` 与默认集群那组（`routes.go` 的 `defaultAPI`，经 `ClusterMiddleware`）以外的
   `/api/v1/clusters`、`/api/v1/projects`、会话探活、公告等都不带。若按正文「没头就清除」，
   这些响应的完成会把提示冲掉——页面提示会随着它们的节奏反复闪。现行判据：带 `X-Cluster-Data-Age`
   却没有 `X-Cluster-Data-Stale` 即「后端确认数据是新的」，立刻清除，自动恢复的语义不变。
2. **探活不走 `Discovery().ServerVersion()`，改走 `kube.ProbeServerVersion`**（§5.2）。前者把 context 写死成
   `context.TODO()`，3 秒超时落不到它身上，集群不可达时 TCP 可能等到系统级超时。现在直接对
   `/version` 发一次带 deadline 的请求；`shouldUpdateCluster` 里那次 `ServerVersion()` 的结果被复用为探活结果，
   不为同一轮同步多发请求。
3. **「探活连续失败」按 Age 收敛为一条判据**（§5.2）。15s 间隔 × 3 次失败即 45s，与阈值等价，
   所以不再单记失败次数；`RecordProbeError(err)`（不带时刻，失败只得原因）只记录原因、不动 `lastAPIOK`，
   由 Age 增长触发陈旧。另外 `RecordWatchError` 返回 bool（是否该打日志），限频状态放在 `Health` 内部，
   调用方只负责打。
4. **节点状态口径两处与 §4 不同（B，有意取舍）**：`NodeStatusKind` 没用 §4 的枚举，沿用资源列表页
   既有取值（`Ready`、`NotReady`、`Unreachable`、`Ready,SchedulingDisabled`…，压力名也可作 kind），
   展示侧不必为新枚举另做样式；§4 的「Ready=Unknown → Unreachable」改为——纯 `Ready=Unknown`
   （无失联污点、心跳也新鲜）显示「未知」而非「失联」，只有带失联污点、或 `Ready≠True` 且心跳已停
   才算失联（`k8s.ts` 的 `unreachable` 判据）：刚加入、条件缺失的节点也会落 Unknown，直接判失联太激进。
   `pressures` 字段仍按 §4 保留（2026-10-17 补齐展示，见 §11）。

其余实现口径与正文一致：`Health` 的两个信号（watch 错误标记 / 主动探活清除）、`ClusterInfo.stale*`、
响应头名称、env 名称与默认值（15s / 45s）、前端模块级 store + 横幅 + 切换器徽标。

验证：`go test ./pkg/kube/ ./pkg/cluster/ ./pkg/middleware/ ./pkg/common/`、
`vitest run src/lib/cluster-data-staleness.test.ts src/components/refresh-interval-select.test.tsx src/lib/k8s.test.ts`、
前端全量 `vitest run` 与 `tsc --noEmit -p tsconfig.app.json` 均通过。
§5.7 的真实冒烟（停掉 apiserver 观察横幅出现与消失）已于 2026-10-16 在 node1 执行，见 §10。

## 10. 真实冒烟记录（2026-10-16）

环境：`10.100.117.8`（node1）上起 kind 单节点集群 `aerolink-smoke`（v1.31.0），
`make build` 出的单二进制放到 `/opt/aerolink/` 跑在 8080；超管由 `AEROLINK_USERNAME` /
`AEROLINK_PASSWORD` 引导创建，集群由启动时读 `~/.kube/config` 自动导入。
**没有调小任何参数**，跑的就是默认 15s 探活 / 45s 阈值。
停服手法：把 kind 节点容器里 `/etc/kubernetes/manifests/kube-apiserver.yaml` 移走
（kubelet 随即停掉 static pod），恢复即移回。两轮「停服 → 出现 → 恢复 → 消失」都跑通。

| 观察点 | 结果 |
| --- | --- |
| 阈值边界 | Age 30s / 40s 时无 Stale 头，**50s 时出现 `X-Cluster-Data-Stale: 1`**，45s 阈值准确 |
| 陈旧期间响应 | 集群作用域请求仍返回 **200**（缓存对象原样透传），只有响应头能说明异常——正是本功能的前提 |
| 集群列表 | `stale:true`、`staleReason:"unreachable"`，`staleSince` 恰为最后一次成功访问的时刻（两轮分别是 17:01:32 / 17:04:32） |
| 前端横幅 | 自动出现，文案含集群名与时间；「重试」按钮命中有效，且集群未恢复时点击不会误清除提示 |
| 后端日志 | `cluster_manager.go:519] Failed to get server version …`（探活失败）与 `client.go:224] watch error on *v1.Namespace: … cached data for this cluster may be stale until the next successful probe`（watch 错误）均如期出现 |
| 恢复 | 探活一轮（≤15s）内 Age 回到个位数、Stale 头消失、`stale` 字段清空，横幅自动消失 |

顺带印证了 §9 第 1 条的必要性：陈旧期间页面每 10 秒仍在轮询并收到 200，
若按正文「不带该头即清除」，提示会被这些不带头的响应冲掉。

### 10.1 两个遗留问题（2026-10-19 已处置，决定见下）

1. **集群切换器的「数据可能过期」徽标不会自动出现**（§5.3 出口一）。
   `useCurrentClusterList`（`ui/src/lib/api/cluster.ts:27`）是 `staleTime: 5min`、关掉
   `refetchOnWindowFocus` / `refetchOnReconnect`，且**没有 `refetchInterval`**：实测停服 60s 后
   徽标仍缺，刷新页面后才出现。横幅走响应头所以是自动的，两条出口的时效性不一致。
   可选修法是给该查询加 60s 轮询（集群列表很轻），但会改变全局查询行为，需单独确认。
   → **决定（2026-10-19）：保持现状**。不加轮询：全局查询行为的代价大于徽标时效的收益，
   横幅已是自动信号，徽标在下一次列表拉取时补上即可。
2. **横幅里的时间用浏览器时钟反推**。前端按 `Date.now() - Age` 算「最后更新于」，
   实测 node1 与本机时钟差 2 分钟，横幅显示 `17:03:31` 而真实 `staleSince` 是 `17:01:31`。
   NTP 同步的环境下无影响；要严格就用响应头 `Date`（服务器时间）做基准。
   → **决定（2026-10-19）：采纳**，已落地。`reportClusterDataStaleness` 改为按
   响应头 `Date` - `Age` 换算（见 `cluster-data-staleness.ts` 的 `responseClock`），
   `Date` 头缺失或解析失败时回落浏览器时钟；新增 2 个单测（服务器时钟偏差换算、
   非法/缺失回落），该文件 9/9 通过，tsc 与 eslint 通过。

## 12. 心跳提示误报修复（2026-11-07）

现场现象：节点列表里 4 个节点全部 `Ready`、无失联污点、Pod 与用量正常，却同时提示
「心跳已停 4 分钟，数据可能已过期」，且长期存在。

根因：kubelet 的 10 秒级心跳走 `kube-node-lease` 的 Lease 对象；Node 对象 `status` 只在
状态变化时立即上报，状态不变时按 `nodeStatusReportFrequency`（默认 5 分钟）补报。§4 的
60 秒阈值建立在「kubelet 每 10s 上报 Node.status」的假设上，与真实节拍不符：健康节点在两次
补报之间就会被判「心跳已停」，且浏览器时钟偏差会进一步放大幅度（§10.1 第 2 条已记录现场
时钟差 2 分钟）。

调整（口径只改展示，不改失联判定）：

- `Ready=True` 的节点不再做心跳提示，`NodeStatus` 移除 `heartbeatStale` / `heartbeatAgeMs` 字段；
- 60 秒阈值只保留在 `unreachable` 的兜底判据里（`Ready != True` 且心跳超阈值），用于失联污点
  尚未写入的极短窗口；
- 节点掉线仍由 node-controller 在 grace period 内写回 `Ready=Unknown` / `unreachable` 污点，
  列表与详情照常显示「失联」；节点自报异常（`Ready=False`）显示「未就绪」；
- 缓存陈旧继续由「无法访问集群…」横幅（响应头 `X-Cluster-Data-Stale`）负责。

回归测试：`ui/src/lib/k8s.test.ts` 的「Ready=True 但 lastHeartbeatTime 超过 5 分钟未更新：
不提示、不判失联」与「Ready=False 且心跳新鲜：节点自报未就绪」。i18n 键 `nodes.heartbeatStale`
随之删除。
