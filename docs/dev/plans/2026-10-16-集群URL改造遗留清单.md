## V1 三库直连验证

**为什么必须做**：`clusters.slug` 是新增的 `*string varchar(64)` + 唯一索引，而这条改动
此前只在 SQLite 上跑过（`go test ./pkg/cluster ./pkg/model ./pkg/common` 全绿）。
`AGENTS.md` 与 `docs/dev/cross-database-compatibility.md` 都要求：改完 SQL 除了 SQLite 单测，
还要**直连 MySQL（严格模式）与 PostgreSQL 各跑一遍真实函数**。单测覆盖不到的点：

- 可空列 + 唯一索引：多行 NULL 在 MySQL / PostgreSQL 的唯一索引下是否合法（方案 R9 的前提）；
- `AutoMigrate` 给**既有表**加列并建唯一索引是否成功（PostgreSQL 还要求应用账号是表 owner）；
- `Update("slug", slug)` 的列名引用（MySQL 保留字风险）；
- 回填的全局去重与幂等。

**做法**：起两个一次性容器（端口避开本机既有服务），在 `tools/` 下放临时 main，
按「老库 → 应用重启 → 迁移回填」**分两步**跑（`STEP=seed` / `STEP=migrate`），跑完删掉：

```bash
docker run -d --name aerolink-xdb-mysql -e MYSQL_ROOT_PASSWORD=xdbRoot123 \
  -e MYSQL_DATABASE=aerolink_xdb -p 3307:3306 mysql:8.0.33 \
  --sql-mode=STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION
docker run -d --name aerolink-xdb-pg -e POSTGRES_PASSWORD=xdbRoot123 \
  -e POSTGRES_DB=aerolink_xdb -p 5433:5432 postgres:16-alpine

# 1) 造出「老库」：有集群数据（中文名 / 纯符号名 / 超长名）、没有 slug 列
DB_TYPE=mysql DB_DSN='root:xdbRoot123@tcp(127.0.0.1:3307)/aerolink_xdb?charset=utf8mb4&parseTime=True&loc=Local' \
  STEP=seed go run ./tools/xdbcheck
# 2) 模拟应用重启：新进程走 model.InitDB() 的 AutoMigrate 加列 + 回填，并断言结果
DB_TYPE=mysql DB_DSN='root:xdbRoot123@tcp(127.0.0.1:3307)/aerolink_xdb?charset=utf8mb4&parseTime=True&loc=Local' \
  STEP=migrate go run ./tools/xdbcheck
# PostgreSQL 同上，换成 DB_TYPE=postgres 与
# DB_DSN='host=127.0.0.1 port=5433 user=postgres password=xdbRoot123 dbname=aerolink_xdb sslmode=disable TimeZone=Asia/Shanghai'
```

**为什么必须分两步**：合成一步会在**同一个连接**里先查 `clusters`、再 `DROP/ADD COLUMN`、
又查 `clusters`。PostgreSQL 的 pgx v5 默认缓存 prepared statement，复用时会报
`cached plan must not change result type (SQLSTATE 0A000)` —— 这是验证脚本的场景问题，
**不是产品缺陷**：真实升级是「老库 + 新进程」，连接是新建的。但它顺手给迁移代码留了条规则：
同一进程内 `AutoMigrate` 前后不要用同一个连接查同一张表，加列会改结果类型。

**结果（2026-10-16，全部 PASS）**

| 库 | 版本 | 结论 |
| --- | --- | --- |
| SQLite | 本机 3.x | `go test ./pkg/cluster ./pkg/model ./pkg/common` 全绿 |
| MySQL | 8.0.33，`@@sql_mode` 含 `STRICT_TRANS_TABLES` | 加列、唯一索引、回填去重、幂等、冲突拒绝全 PASS |
| PostgreSQL | 16.15 | 同上，全 PASS |

两库上验证到的行为：
- **多行 NULL 合法**：回填前 5 行 `slug` 全为 NULL 可共存，两库都过 —— 这是方案 R9
  「`slug` 必须可空、不能给 default」的前提。
- **回填去重**：5 个名字 → `cluster` / `cluster-2` / `cluster-3` / `a-b-c-xxx…` /
  `prod-cluster`，两库结果一致；再调一次值不变（幂等）。
- **唯一索引生效**：MySQL `Error 1062 ... for key 'clusters.idx_clusters_slug'`、
  PG `duplicate key value violates unique constraint "idx_clusters_slug" (23505)`。
- **一个已知且刻意保留的跨库差异**：`name` 的唯一索引在 MySQL 的 `*_ci` 排序规则下把
  `prod-cluster` 与 `PROD-CLUSTER` 视为重复，PG 下是两个。`slug` 按精确匹配使用，不受影响。

**踩过的坑（写给下一个做验证的人）**：临时程序必须自己读 `DB_TYPE`/`DB_DSN` ——
`pkg/common` 只在 `internal/config` 加载时才读环境变量，直接调 `model.InitDB()` 会静默落到
默认的 SQLite `dev.db`；第一版脚本因此清空了本地开发库的 `clusters` 表（已用 9/21 的备份
`dev.db.bak-20260924-002032` 恢复回 3 个集群）。脚本现在有两道闸：缺 `DB_TYPE`/`DB_DSN`
直接退出，`DB_TYPE=sqlite` 直接拒绝。

### V1-b `tools/apismoke` 三库冒烟（2026-10-16）

`AGENTS.md` 的这两条要求是分开的：「直连 MySQL/PostgreSQL 各跑一遍**真实函数**」与
「跨功能面的改动再用 `tools/apismoke` 对每套库跑一遍**冒烟**」。上面 V1 验的是 `clusters.slug`
这一列；本次改造同时动了路由、集群上下文与全站导航，属于跨功能面，所以要再跑一遍冒烟。

**做法**：三套实例（`PORT` 18080/18081/18082），只换 `DB_TYPE`/`DB_DSN`，其余共用 `dev.env`
与 `config.dev.yaml`（超管 `admin` 由 `config.dev.yaml` 的 `superUser` 段播种，库里为空时自动建）；
三个库分别是 SQLite 临时文件、容器 `aerolink-xdb-mysql`（8.0.33，`--sql-mode` 带
`STRICT_TRANS_TABLES`）、容器 `aerolink-xdb-pg`（16-alpine）。冒烟需要有**能连通的集群**，
所以三套实例各手工导入一份本机 kind 集群 `aerolink-e2e` 的 kubeconfig：

```bash
DB_TYPE=mysql DB_DSN='root:xdbRoot123@tcp(127.0.0.1:3307)/aerolink_xdb?charset=utf8mb4&parseTime=True&loc=Local' \
  PORT=18081 AEROLINK_AUDIT_SINK=database ./aerolink
curl -s -b jar -X POST http://127.0.0.1:18081/api/v1/admin/clusters/import -H 'Content-Type: application/json' \
  --data-binary @<(python3 -c "import json;print(json.dumps({'config':open('kind.kubeconfig').read()}))")
go run ./tools/apismoke -base-url http://127.0.0.1:18081 -username admin -password 'AdminPass!234' \
  -cluster kind-aerolink-e2e -namespace default -write-namespace default -log-file /tmp/smoke-mysql.log
```

**结果（2026-10-16）：三库全部 83/83 通过**（读检查 54 + 写检查 29），三库的
「服务端日志无数据库错误」均为 PASS。

| 库 | 版本 | apismoke | 建表数 |
| --- | --- | --- | --- |
| SQLite | 3.46.1 | 83/83 | 34（多一张 `sqlite_sequence`） |
| MySQL | 8.0.33（`STRICT_TRANS_TABLES`） | 83/83 | 33 |
| PostgreSQL | 16.15 | 83/83 | 33 |

两个与库无关、但会让人误判成跨库缺陷的坑：
- `AEROLINK_AUDIT_SINK` 用默认的 `parquet` 时，「Deployment 历史」接口按设计返回 501
  （`resource_history_requires_database_sink`），读检查会掉一项（54 → 53）。跑跨库冒烟请用
  `database`。
- `config.dev.yaml` 的 `clusters` 段是空的，而且设了 `AEROLINK_CONFIG_FILE` 之后 `KUBECONFIG`
  自动导入也不再生效 —— 集群必须手工导入，否则 `apismoke` 在 `prepare` 阶段就中断。

### V3 仍未覆盖：MySQL 5.7（表格里那一项）

本机既没有 5.7 实例也没有镜像，离线环境拉不到。风险点是 5.7 的 utf8mb4 索引前缀长度上限，
口径见 `docs/dev/cross-database-compatibility.md` 末尾的「MySQL 5.7 的老版本风险」：767 字节
上限只对 **5.7.7 之前**（或 `innodb_large_prefix=OFF`、`ROW_FORMAT=COMPACT`）成立，5.7.7 起
默认 3072 字节。本次是 `varchar(64)` 单列唯一索引，utf8mb4 下 256 字节，即使按老上限也远未
触顶，官方镜像 5.7.44 更没有问题 —— 所以风险很低，**不影响本次改造可用**。

**补跑口径**（有条件时）：V1 的两条命令换成 5.7 实例（`mysql:5.7` 镜像、`--sql-mode` 同样带
`STRICT_TRANS_TABLES`）；V1-b 的冒烟同理换 `DB_TYPE`/`DB_DSN` 与 `PORT` 再跑一遍，并保持
`AEROLINK_AUDIT_SINK=database`。跑前先确认两个前提，否则会拿到「修复前也通过」的假结果：

```sql
SELECT @@sql_mode;                         -- 必须含 STRICT_TRANS_TABLES
SHOW VARIABLES LIKE 'innodb_large_prefix'; -- 应为 ON；为 OFF 才是真正的风险点
```

## 刻意不做（决策，不是欠账）

- **初始化向导的导入步骤不置灰**：向导只在未初始化时可达，那时平台里通常还没有集群，
  不存在「同名已存在」；真在已有集群的实例上重跑向导，同名行仍可手填（值被后端忽略）。
  向导是否可达由 `init-check-route` 决定（方案 §11「仍然开放」）。
- **向导用共享 `ClusterSlugFields` 而不是 `ClusterImportDialog`**：in-cluster 模式没有
  kubeconfig 文本，套 modal 会多出一条提交路径。
- **`kubeconfig.ts` 不读 `current-context`**：逐行短名要的是全部 context，与方案 §5 原文
  的表述有偏差（§11 已记）。
- **方案 §3.8 明确不做**：服务端不解析 slug（鉴权 / RBAC / 审计路径零改动）、不动业务
  API 契约（`/_clusters/:cluster` 分组语义、`ClusterMiddleware`、`x-cluster-name` 不变）、
  不做子域方案、不做查询参数方案、不保留无前缀业务路径长期可访问（只重定向）。
