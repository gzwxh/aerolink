## 1. 目标

在交付用户前，通过分层自动化测试、真实集群验收和正式部署形态验证，尽早发现以下问题：

1. 服务无法构建、启动、迁移数据库或通过健康检查。
2. Pod 历史日志、实时日志、过滤、下载及审计归档检索结果不正确。
3. 终端、文件管理、WebSocket、SSE 或反向代理链路不可用。
4. Kubernetes 资源增删改查、扩缩容、重启、回滚、Helm 等功能异常。
5. 登录、用户管理、RBAC、API Key、外部认证存在越权或失效。
6. SQLite、MySQL、PostgreSQL 之间行为不一致，升级后缺表、缺列或回填失败。
7. 已部署实例与开发环境表现不一致。

本方案用于降低交付风险，不把“测试通过”表述为绝对没有任何缺陷。未执行、被跳过或环境不具备的用例必须单独列出，不能计入通过。

## 3. 测试环境划分

| 环境 | 用途 | 数据与风险边界 |
| --- | --- | --- |
| 本机单元/组件测试 | Go、Vitest、静态检查、构建 | 不访问真实业务集群 |
| 独立 kind 集群 | 完整、可重复的 28 组 Playwright E2E | 使用全新临时 SQLite 和临时实例，最适合破坏性用例 |
| `devops-wxh` + 本机临时实例 | 验证真实 Kubernetes 版本、节点、镜像、存储和网络兼容性 | 临时实例监听 `127.0.0.1:38080`；会真实创建、修改、删除集群资源 |
| `10.100.117.5:8080` | 对已部署实例做 API 冒烟、日志/终端和代理链路验收 | 不直接对其跑完整 Playwright setup；写冒烟仅使用指定测试命名空间和 `smoke-` 前缀资源 |
| 正式部署形态预验收 | 验证最终镜像、Chart values、数据库、Ingress、PVC 和副本数 | 使用发布候选产物，尽量与用户交付拓扑一致 |

### 关键限制

不能直接给完整 Playwright 套件设置 `AEROLINK_E2E_BASE_URL=http://10.100.117.5:8080` 后运行。其 setup 会进入 `/setup` 创建初始管理员并导入集群，要求一套尚未初始化的新实例；对现有实例直接跑会失败，也可能破坏已有用户和设置。

正确方式是：由 E2E 启动本机全新临时实例，再把 `devops-wxh` 的 kubeconfig 导入临时实例。

```text

```

两者会临时修改实例设置并尝试恢复。执行前备份相关设置，执行后人工核对。应用运行在另一台机器或 Pod 内时，不能假设它能访问运行 `apismoke` 机器的 `127.0.0.1`。

## 9. 阶段五：日志、终端与审计专项

这是强制人工/浏览器验收项。现有 `resource-detail.spec.ts` 只断言日志过滤框和 `.xterm` 出现，没有完整断言日志内容，也没有执行终端命令，不能据此认定日志查询正确。

### 9.1 准备可核对的日志 Pod

```bash
export TEST_IMAGE='<集群可拉取且包含 /bin/sh 的镜像>'

kubectl --kubeconfig="$DEVOPS_KUBECONFIG" \
  -n aerolink-check run log-content-check \
  --image="$TEST_IMAGE" --restart=Never \
  --command -- sh -c \
  'i=1; while [ "$i" -le 100 ]; do echo "AEROLINK_STATIC seq=$i"; i=$((i+1)); done; sleep 3600'

kubectl --kubeconfig="$DEVOPS_KUBECONFIG" \
  -n aerolink-check run log-stream-check \
  --image="$TEST_IMAGE" --restart=Never \
  --command -- sh -c \
  'i=0; while true; do i=$((i+1)); echo "AEROLINK_STREAM $(date -u +%FT%TZ) seq=$i"; sleep 2; done'

kubectl --kubeconfig="$DEVOPS_KUBECONFIG" -n aerolink-check wait \
  --for=condition=Ready pod/log-content-check pod/log-stream-check \
  --timeout=120s
```

### 9.2 历史日志正确性

以 `kubectl logs` 为基准：

```bash
kubectl --kubeconfig="$DEVOPS_KUBECONFIG" \
  -n aerolink-check logs log-content-check --tail=20 \
  > /tmp/aerolink-log-tail20.txt

kubectl --kubeconfig="$DEVOPS_KUBECONFIG" \
  -n aerolink-check logs log-content-check --timestamps \
  > /tmp/aerolink-log-timestamps.txt
```

在 AeroLink 页面逐项核对：

1. `tailLines=20` 应只包含 `seq=81` 至 `seq=100`，顺序一致、无缺失和重复。
2. 全量日志应包含 100 条固定记录；过滤 `seq=42` 只命中对应行。
3. 清空过滤后恢复完整内容，切换过滤条件不应串入其他 Pod 或容器日志。
4. 时间戳开关与 `kubectl logs --timestamps` 的时间含义一致，时区显示有明确口径。
5. 下载日志的行数、顺序和内容与页面选择及 kubectl 基准一致。
6. 多容器 Pod 逐容器核对，容器切换后不能显示上一个容器的数据。
7. 对有重启记录的容器检查 previous 日志；不存在 previous 时应有明确提示，而不是返回当前日志冒充。

### 9.3 实时日志与重连

1. 打开 `log-stream-check`，确认历史 tail 先出现，随后约每两秒追加一条。
2. 检查序号连续性，观察期间无重复、丢行或旧内容被错误清空。
3. 切换 `tailLines`、时间戳和容器后，确认 WebSocket 按预期重连。
4. 切走页面再回来、切换工作区会话，确认行为符合设计且没有无限新增后台连接。
5. 关闭日志会话后，服务端流应取消；结合服务端日志确认没有持续 goroutine/连接泄漏迹象。
6. 经正式 Ingress 访问时，在浏览器 Network 中确认 WebSocket 为 `101 Switching Protocols`。

### 9.4 终端与文件管理

在 `log-stream-check` 的终端执行：

```sh
echo aerolink-terminal-ok
pwd
stty size
```

检查：

- 命令及输出完整，无丢字符；粘贴较长文本时尾部不丢失。
- 调整浏览器和工作区大小后，`stty size` 与显示尺寸同步。
- 同时保留日志和终端会话，切换页签不会互相覆盖或异常断开。
- 文件列表、下载、上传及内容校验正确；上传下载前后计算 SHA-256。
- 通过正式代理入口验证 WebSocket Upgrade，而不只是 localhost 可用。
- 会话结束后检查相关 Agent/临时资源清理。

### 9.5 日志与终端权限

使用受限账号分别验证：

- 有 `pods/log` 权限才能看日志，无权限时明确拒绝。
- Pod 终端需要 `pods/exec`，选择目标还需要 `pods/get`。
- 节点终端需要 `nodes/exec`。
- Kubectl 终端要求管理员且通用设置已开启。
- 前端隐藏按钮不能作为权限结论，必须直接请求 API/WebSocket 验证后端 fail-closed。
- AI 读取日志也沿用同一用户权限，不得绕过 RBAC。

### 9.6 审计日志与归档检索

1. 制造一次成功登录和一次失败登录。
2. 创建、更新、删除名称唯一的 ConfigMap。
3. 执行一次文件上传、下载和一次密码修改。
4. 分别在登录日志、操作日志、文件操作和改密日志中按用户、时间、资源和动作检索。
5. 打开资源历史，核对 create/update/patch/delete 记录。
6. 导出 CSV，核对记录内容与筛选条件；有响应哈希时与文件 SHA-256 对照。
7. 确认没有修改或删除单条审计记录的业务入口。
8. parquet 归档等待实际 flush 间隔后再查，不能把“刚写入尚未归档”误判为检索失败。
9. 如果启用 S3、ES、VictoriaLogs、OpenObserve、Kafka 等外部 sink，分别验证写入、检索、服务中断和恢复。

## 10. 阶段六：正式部署形态与启动验收

必须使用最终交付产物，而不能只验证 `make dev`。

### 10.1 镜像和 Chart

1. 使用与发布一致的入口构建镜像：`make image` 或满足 glibc 条件时使用 `make image-binary`。

4. 使用交付 values 在独立命名空间执行 Helm 安装/升级，等待 rollout 完成。

### 10.2 启动场景

至少覆盖：

- 空数据库首次启动和自动建表。
- 同一数据目录/数据库上的进程重启。
- 上一发布版本数据升级到当前候选版本。
- 使用生产同等权限的数据库账号，而不只是 root/owner。
- 正式 Ingress、TLS、`TRUSTED_PROXIES` 和代理超时配置。
- 正式副本数；多副本时检查设置传播、会话、WebSocket 和共享存储。

每次检查：

```bash
curl -fsS http://10.100.117.5:8080/healthz
curl -fsS http://10.100.117.5:8080/api/v1/version
```

并核对：

- 所有 Pod Ready，rollout 和重启次数正常。
- `/api/v1/version` 与发布版本一致。
- 服务日志无数据库连接、缺表、缺列、SQLSTATE 42501、MySQL 1064/1054/1292、迁移和回填错误。
- 无审计 sink 配置错误、DuckDB/parquet 初始化错误及反复重启。
- 设置 `AEROLINK_LOG_FILE` 后，Info 级日志可能只写文件；不能只凭 `kubectl logs` 没有异常就跳过日志文件检查。

### 10.3 库结构升级

```bash
git diff <上一个tag>..HEAD -- pkg/model/
```

有模型列、索引或 `Migrate*Backfill` 变化时：

1. 按 `docs/dev/release-checklist.md` 准备三库等价 SQL 和权限说明。
2. 升级前在预验收库执行对应 SQL；PostgreSQL 确认执行账号为表 owner。
3. 升级后检查 `checkSchema()` 输出，不得存在缺表/缺列。
4. 有回填时不能简单设置 `DB_MIGRATE=off` 跳过。
5. 在发布说明中单列升级动作，不能只写一行 `feat(db)`。

## 11. 阶段七：数据库矩阵

### 必测原则

- 至少测试用户实际使用的数据库及版本。
- 如果本次交付继续承诺 SQLite、MySQL 5.7/8.x、PostgreSQL 12+ 全部支持，则三类数据库都要做真实实例测试。
- CI 和多数 Go 单测主要覆盖 SQLite，不能代替 MySQL/PostgreSQL 实库验证。

每种数据库执行：

1. 创建全新数据库，启动应用，确认自动建表成功。
2. 导入 `devops-wxh` 或独立测试集群，执行登录、资源读取和加解密配置读取。
3. 跑 `tools/apismoke` 只读和写检查。
4. 重启应用，确认重复迁移、数据回填和已有数据读取正常。
5. 验证中文、emoji、时间、自增主键、分页、模糊查询、可空列排序和审计导出。
6. 扫描服务端 SQL 和迁移错误。

MySQL 必须先检查 `@@sql_mode`，至少覆盖严格模式；PostgreSQL 应覆盖支持的最低大版本及实际交付版本。静态 SQL 扫描测试不能代替真实数据库执行。

## 12. 自动化之外的手工验收矩阵

| 功能面 | 必须补充的验收 |
| --- | --- |
| 真实外部认证 | 企业 LDAP/OIDC、错误密码、组映射、allowed groups、真实 MFA 扫码和错误动态码 |
| 会话与安全 | HTTPS Secure Cookie、IP 黑白名单、登录锁定、代理头、会话顶替、禁用用户后的旧会话 |
| AI | 真实 provider 鉴权和模型兼容性、SSE 不缓冲、读资源/日志、写操作确认与拒绝、受限用户 RBAC |
| 通知 | 真实 SMTP/Webhook 投递、失败重试和设置恢复，不只检查页面保存 |
| 审计外部后端 | 实际启用的 S3/ES/VictoriaLogs/OpenObserve/Kafka 全链路及故障恢复 |
| 浏览器 | Playwright 当前主要跑 Chromium；按用户环境补 Firefox、Safari/iOS 和基线版本检查 |
| 多副本与代理 | 跨副本请求、日志/终端 WebSocket、AI SSE、文件上传下载和共享审计存储 |
| 异常路径 | 无效 kubeconfig、集群不可达、镜像拉取失败、数据库断开、外部服务超时和恢复 |

未启用的功能可以标记为“不适用”，但必须写明依据；启用了却未测试的功能不能标记通过。
