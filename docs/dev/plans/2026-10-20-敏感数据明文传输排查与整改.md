# 敏感数据明文传输排查与整改

- 日期：2026-10-20
- 状态：**P1 / P2 / P3 的应用侧均已实施**（P0 的 TLS 属部署侧动作；实施记录见 §7、§8）。响应侧已收口一项：API Key 列表不再下发可用密钥（§8.6）；P0 的应用侧部分——入口一致性闸已实现（§8.7），随 `HOST` 自动生效；P3 强制模式已实现但**默认关闭**（§8.8），由部署方在客户端全部升级后开启
- 触发：`http://aerolink.gogdev.cn/login` 登录请求体里的 `password` 是明文，用户提出按同一类问题全量排查后统一整改。

## 1. 结论

1. **根因不在请求体，在链路**：应用二进制只监听 HTTP（`main.go:97-107` 的 `http.Server` + `ListenAndServe`，全仓库无 `ListenAndServeTLS` / 无 TLS 配置项），
   `deploy/nginx-aerolink.conf:28` 只 `listen 8080`，`charts/aerolink/values.yaml:359-370` 的 `ingress.enabled` 默认 `false` 且 `tls` 段是注释。
   当前对外域名是可访问的 **`http://`**，所以泄漏面远不止登录密码：**会话 Cookie、全部接口响应、WebSocket 终端、上传下载** 都在明文链路上。
2. 因此整改顺序必须是 **先 TLS（P0），再敏感字段的应用层加密（P1/P2）**。反过来做（只加密密码）会被误读成"已经安全"，而同一页面上的 token、kubeconfig、Secret 仍是明文。
3. 应用层加密仍有独立价值：它挡住的是 **TLS 之外** 的泄漏面——反向代理/WAF/负载均衡的访问日志与镜像、APM 与抓包留存、浏览器扩展与 DevTools 抓包、被误配成 `http` 的入口。定位是纵深防御，不是 TLS 替代品。
4. 本机实例（`http://192.168.100.8:8080`，不经任何入口）同样复现明文登录，说明这是应用自身的行为，不是某个部署环境的配置失误；整改只能在应用内完成，P0 的 TLS 属于并行要求而非前置条件。
5. 已核实**不是**问题的相邻项：管理审计中间件只从请求体挑标识字段落库，不落全量 body（`pkg/middleware/audit.go:72-83`、`:110-112`）；审计出口配置变更只记"密钥是否变更"，不留明文（`pkg/audit/setting.go:264-266`）；Cookie 已是 `HttpOnly` + `SameSite=Lax`，且在 `https` 下自动带 `Secure`（`pkg/auth/login_handler.go` 的 `setCookieSecure`，测试见 `pkg/auth/login_handler_test.go:50-105`）；HSTS 只在 TLS 下下发（`pkg/middleware/security_headers.go:46-49`）。

## 2. 传输面现状

```
浏览器 --HTTP(明文)--> 入口(nginx / Ingress) --HTTP--> aerolink 副本 (:8080)
```

- 应用不终结 TLS；`HOST` 环境变量（如 `https://aerolink.example.com`，见 `README.md:173`、`charts/aerolink/values.yaml:38-40`）只影响 Cookie 的 `Secure` 属性与 OAuth 回调拼接。
- `charts/aerolink/templates/ingress.yaml:17-26` 支持 `ingress.tls`，但默认未启用（`values.yaml:368-370`）。
- `deploy/nginx-aerolink.conf` 是多副本样例，同样只有 8080，没有 443/301。
- WebSocket（容器终端、日志跟随）经 `proxy_set_header Upgrade ...` 透传，HTTP 下即 `ws://`，终端里的键盘输入与输出全明文。

### 复核方法（任何人可复现）

1. 浏览器打开 `http://aerolink.gogdev.cn/login`，开发者工具 → Network → 抓 `POST /api/auth/login/password`，请求体可见 `{"username":"...","password":"..."}`。
2. `curl -i http://<host>/api/auth/login/password -H 'Content-Type: application/json' -d '{"username":"u","password":"p"}'` 能直接发起登录。
3. `curl -s http://<host>/login | head` 与浏览器地址栏一致为 `http`；页面资源、`Set-Cookie` 均无 TLS 保护。

## 4. 方案

### 4.1 P0：先把链路变成 HTTPS（必做，且优先级最高）

1. 入口层：Ingress 启用 `ingress.tls`（`charts/aerolink/values.yaml:368-370` 打开并填 `secretName`），或 nginx 增加 `listen 443 ssl` 与 80→443 的 301（`deploy/nginx-aerolink.conf` 补一段）。
2. 应用层配合：`HOST` 配成 `https://…`，使 Cookie 带 `Secure`（已实现）；`X-Forwarded-Proto` 必须由入口透传，否则 HSTS 与 `Secure` 都不会生效（`pkg/middleware/security_headers.go:47`）。
3. 建议新增一个**入口一致性闸**（小改动、fail-closed）：当 `HOST` 是 `https://` 而本次请求既无 TLS 也无 `X-Forwarded-Proto: https` 时，对 `/api/auth/login/*`、`/api/users/me/password`、`/api/admin/*` 直接 400，提示"必须通过 HTTPS 访问"。避免"证书配好了但有人用 http 直连后端/绕过入口"。
   ——**已实施**：`pkg/middleware/require_https.go`（登记见 §8.7），随 `HOST` 自动生效，无需新配置。
4. 部署检查清单（写进运维文档）：证书有效期监控、HSTS 是否下发、`curl -I https://<host>` 有 `Strict-Transport-Security`。

### 4.2 P1/P2：请求体敏感字段加密（纵深防御）

**明确不做**：前端把口令做 hash/摘要后上传——那会让摘要本身变成口令（重放即可登录）；也不引入第三方 JS 加密库（`ui` 现有依赖里没有，且 WebCrypto 在浏览器基线内可用）。

**协议**

- 新增 `GET /api/transport-key`（免认证、限流）：返回 `{key_id, alg, public_key, nonce, expires_at}`。
  - `alg`：`RSA-OAEP-256`（2048 位起步，优先 3072）。
  - `nonce`：一次性、60s 过期；服务端缓存后用即删，用于防**密文重放**（否则截获密文可原样重放）。
  - 多副本部署下 nonce 与私钥必须跨副本一致：私钥由部署注入（`AEROLINK_TRANSPORT_KEY_PATH`），nonce 复用既有的多副本共享状态（PostgreSQL），不要放进程内存（参见 `2026-09-20-多副本共享状态.md`）。
- 两类载荷：

  | 类型 | 适用 | 做法 |
  | --- | --- | --- |
  | 短字段（≤190 字节） | 口令、MFA 码、AK/SK、SMTP/Kafka/ES 口令 | `RSA-OAEP(JSON{nonce, fields})` 直接作为字段值，键名加 `_enc` 后缀 |
  | 长文本 | kubeconfig、Secret `data`、Helm `values`、审计设置整包 | 信封加密：前端随机 AES-256-GCM 会话密钥 → 加密载荷 → RSA 包封会话密钥，请求体为 `{"enc":{"key_id","wrapped_key","iv","ciphertext"}}` |

- 前端：`ui/src/lib/crypto/transport.ts` 提供 `encryptFields()` / `encryptEnvelope()`，由 `ApiClient.post/put/patch` 统一按"敏感路径白名单"处理，业务代码不感知；公钥按 `key_id` 缓存，过期或解密失败自动重取一次。
- 后端：`pkg/crypto/transport`（解密 + nonce 校验），在各 handler 的 `ShouldBindJSON` 之后统一解包；解密失败返回 `400 {"code":"encrypted_payload_invalid"}`，**不得**把密文或明文写进日志。
- 兼容与灰度：后端**同时接受**明文与密文；配置 `AEROLINK_REQUIRE_ENCRYPTED_CREDENTIALS=true` 时只收密文（默认 false）。前端在收到"不支持"（404 / 未知字段）时回退明文一次，便于滚动升级。

### 4.3 与现有机制的衔接

- 审计中间件：`pkg/middleware/audit.go` 只取 `username/name/ip/...` 做对象名。字段改名成 `*_enc` 后，这些标识字段**保持明文**（它们不敏感），否则审计日志的对象名会全部变成 `#id`。
- 登录限流、验证码、MFA、Cookie 逻辑不变，加密只发生在"进入 handler 之前"。
- 工具链：`tools/apismoke` 与 `e2e/specs/*.spec.ts` 原本直接发明文——靠兼容期继续可用。已按"不能靠关掉强制绕过"的口径适配：apismoke 收到 `encrypted_credential_required` 后自动取公钥加密重试一次（§8.8），e2e 由 `E2E_ENCRYPT_CREDENTIALS=1` 切到密文路径。

## 5. 分期与验收

| 阶段 | 范围 | 验收 |
| --- | --- | --- |
| P0 | HTTPS 入口 + 301 + `HOST`/`X-Forwarded-Proto` 校验 + 入口一致性闸（闸门已实现，见 §8.7；其余是部署侧动作） | 浏览器地址栏为 `https`；`http://` 自动 301；`curl -I` 见 HSTS；抓包看不到明文；`Set-Cookie` 带 `Secure`；`HOST=https` 后 `curl http://…/api/v1/admin/apikeys/` 返回 400 `https_required` |
| P1 | `GET /api/transport-key` + 解密中间件 + 3.1 全部字段（含 LDAP/超管/重置/MFA） | 抓包只见密文；nonce 重放被拒；过期被拒；错误口令仍走既有失败限流；关掉前端加密开关后接口仍可用（兼容） |
| P2 | 3.2 / 3.3 的短字段与长文本信封加密 | kubeconfig、Secret、审计外发、SMTP、AI Key、Helm 凭据均以密文上行；非敏感字段仍便于审计 |
| P3 | 强制模式（`AEROLINK_REQUIRE_ENCRYPTED_CREDENTIALS`，默认 `false`，见 §8.8）；响应侧整改（API Key 只在创建时返回一次已完成，§8.6） | 开关打开后无明文兼容路径；工具链适配完成（§8.8 已验证） |

回归测试（每阶段补一条聚焦用例）：解密成功；nonce 复用拒绝；`expires_at` 过期拒绝；强制模式下明文被拒（400 + 明确 code）；密文损坏不产生 panic、不写日志。

## 6. 风险与取舍

- **加密请求体不等于安全**：中间人仍可完整重放合法密文（nonce 只能挡同一个 nonce 的第二次使用），也可篡改响应。没有 TLS 时，这套机制只降低"日志/抓包留痕"风险。
- **私钥管理是新的运维项**：私钥丢失 → 所有写操作不可用；私钥泄漏且无 TLS → 等于没有加密。必须纳入发布检查清单，不能像 `JWT_SECRET` 那样随手 `openssl rand` 后丢弃。
- **性能**：RSA 只用于会话密钥/短字段，长文本走 AES-GCM，开销可忽略；但上传（头像、容器文件）与日志流不做加密，仍靠 TLS。
- **可观测性**：`captcha_code`、`mfa_code` 加密后，排障时看不到原值——这是期望行为，需在排障手册里写明"只能看 `code`，不能看内容"。

一个实现细节值得记下来：**WebCrypto 只在安全上下文可用**（https / localhost）。最初只写了
`crypto.subtle.importKey`，用 `http://192.168.100.8:8080` 打开时前端报

"口令别进日志"，不改变无 TLS 时可被中间人看到全链路的事实。

`pkg/auth` 的 `TestPendingMFAVerifyAcceptsEncryptedCode`（各含一条篡改密文必须 400 的断言）。

## 8. 已实施（2026-10-20，第二阶段：P2 长文本与配置类凭据）

P1 只解决了短口令字段（RSA-OAEP 逐字段）。kubeconfig、Secret `data`、Helm `values`、YAML apply
这类长文本塞不进 2048/3072 位 RSA 的明文上限，所以 P2 加了一层**整包信封**，改由前端对整段请求体
加密，服务端在业务 handler 之前还原。

### 8.1 信封格式

```json
{"enc":{"v":1,"key_id":"…","alg":"RSA-OAEP-256+AES-256-CTR-HMAC-SHA256",
        "wrapped_key":"<base64>","iv":"<base64>","data":"<base64>","mac":"<base64>"}}
```

- 会话密钥 64 字节：前 32 字节 AES-256-CTR，后 32 字节 HMAC-SHA256。
- 明文是 `{"ts":<unix 秒>,"body":<原始 JSON 请求体>}`；`ts` 复用既有的 `MaxAge`（±300s）判重放/过期。
- **encrypt-then-MAC**：`mac = HMAC(hmacKey, iv‖data)`，解密侧先验 MAC 再进 AES，被篡改的密文不会产生
  可观测的时间差，也不会被当成合法密文送去 `json.Unmarshal`。
- 只有 `key_id` 与 `alg` 在密文外（代理日志里可见），正文与时间戳都在 MAC 保护范围内。

**为什么不用 AES-GCM**（方案 §4.2 原稿写的是 GCM）：`crypto.subtle` 只在安全上下文存在，
`http://<内网IP>` 打开时没有 WebCrypto，只能走纯 JS。纯 JS 的 GHASH 比 HMAC-SHA256 难写得多，
而 SHA-256/HMAC 已经有实现（`ui/src/lib/sha256.ts`）并且有 OpenSSL 交叉验证的测试。
CTR+HMAC 与 GCM 在"先验后解"的前提下安全性等价，成本是密文多 32 字节 MAC。

### 8.7 入口一致性闸（P0 的应用侧部分）

TLS 与 301 属于部署侧动作（Ingress / nginx），这里只把「应用层能自查的那半边」补上：
`HOST=https://…` 说明对外应该是 HTTPS，若这时还有请求是明文进来的，说明入口配错了
（或有人绕过入口直连后端），凭据类接口应当当场拒绝而不是照常处理。

| 项 | 实现 |
| --- | --- |
| 位置 | `pkg/middleware/require_https.go`，在 `app.go` 的 `buildEngine` 里挂在 `Logger()` 之后（被拒的请求也留访问日志）、`DevCORS` 之前 |
| 生效条件 | `HOST` 以 `https://` 开头才启用；默认（`HOST` 为空或 http）整条闸门关闭，纯 HTTP 部署零影响 |
| 判定为安全 | 本次请求 `r.TLS != nil`，或 `X-Forwarded-Proto` 第一段（多级代理会给 `https, http`）等于 `https` |
| 拦截范围 | `/api/auth/login`（含 `login/password`、`login/ldap`）、`/api/users/me/password`、`/api/v1/admin` —— 按路径段边界匹配，并带 `BASE` 前缀 |
| 不拦截 | `/healthz` 等探针、SPA 静态资源、WebSocket 终端（见下） |
| 响应 | `400 {"code":"https_required","error":"This endpoint must be accessed over HTTPS"}`；`ApiError` 已带 `code`，将来前端可按需翻译 |

两点说明：

- **它不是认证边界**：能直连后端的攻击者本就能自己伪造 `X-Forwarded-Proto: https`。这条闸门治的是
  「证书配好了却有人走明文」的配置错，那种场景只能靠网络策略（后端只监听内网、只对入口放行）解决。
  之所以仍按 `HOST` 自动生效、不新增开关：漏开等于没做，误伤只会出现在「`HOST` 写了 https 但入口没
  透传转发头」这种本来就该修的部署上。
- **探针必须放过**：`/api/health` 通常由 kubelet 以 http 直连 Pod 探活，把它一起收紧的结果是 Pod
  反复重启，而不是更安全。同理 SPA 入口页不含秘密，锁死只会让用户看到一片空白、连提示都加载不出来。
- WebSocket 终端/日志流没有纳入闸门：握手阶段没有可加密的凭据字段，`HOST=https` 下的握手同样带
  `auth_token` Cookie，收紧它需要与 Cookie 判定完全一致，留给 P0 的 TLS 一并解决（§3 已按该口径登记）。

回归用例 `pkg/middleware/require_https_test.go` 覆盖：闸门关闭时明文放行；开启后三个敏感前缀各自 400
且带 `https_required`；`X-Forwarded-Proto` 为 `https`/`HTTPS`/带空格/`https, http` 放行而 `http` 被拒；
`r.TLS` 放行；探针放行；带 `BASE` 前缀时仍然生效；前缀匹配不误伤 `/api/v1/adminx`、`/api/auth/loginx`。

### 8.8 强制模式（P3，2026-10-20 晚）

一句话：`AEROLINK_REQUIRE_ENCRYPTED_CREDENTIALS=true` 时，凭据字段只有密文这一条路，明文直接
`400 {"code":"encrypted_credential_required"}`。默认 `false`，因为滚动升级窗口里旧页面只会发明文
（内嵌的前端产物与后端是同一个二进制，但浏览器里可能还开着上一版的标签页）。

判定集中在一处，不在每个 handler 里各写一遍：

| 位置 | 改动 |
| --- | --- |
| `pkg/transportkey/http.go` | 新增 `ResolveCredential(c, enc, target)`：有密文走解密；只有明文且开关打开 → 400 + `encrypted_credential_required`；字段整体缺省不拦（留给 handler 报"必填"） |
| `pkg/transportkey/transportkey.go` | 新增错误码 `CodeCredentialRequired`；抽出并导出 `EncryptFieldsWithPublicKey` / `ParsePublicKey`，供只有公钥的调用方（apismoke、e2e）按同一套载荷格式加密 |
| `pkg/common/common.go` | `RequireEncryptedCredentials` 包级开关 + `AEROLINK_REQUIRE_ENCRYPTED_CREDENTIALS` 解析 |
| `pkg/auth/login_handler.go`、`pkg/users/handler.go` | 8 处凭据解析改用 `ResolveCredential`：密码登录、第三方登录补验动态码、超管初始化、创建用户、管理员重置口令、自助改密（当前/新口令）、MFA 绑定时的当前口令、MFA 动态码 |
| `tools/apismoke` | 登录先发明文；响应体里出现 `encrypted_credential_required` 时取 `GET /api/v1/transport-key` 的公钥加密重试一次，并在 stderr 说明——冒烟脚本是来验证部署的，不该因为这条安全开关报假失败 |
| `e2e/support/credentials.ts` | `credentials(request, body)` 把明文凭据换成 `*_enc`；只有 `E2E_ENCRYPT_CREDENTIALS=1` 时生效，默认仍覆盖"明文兼容"这条路径 |
| `README.md`、`charts/aerolink` | 环境变量表 + `requireEncryptedCredentials` value，注释写明"确认客户端已升级后再开，滚动升级期间开会让旧页面登录失败" |

回归用例：`pkg/transportkey/http_test.go`（开关关闭明文通过／开启后明文 400 且带 code／密文解出中文口令／
字段缺省不拦／坏密文仍是 `credential_decrypt_failed`）、`pkg/auth/login_integration_test.go`
（强制模式下明文登录 400、密文登录 204）、`pkg/transportkey/transportkey_test.go`（公钥侧加密能被服务端解开）。

真实二进制冒烟（`AEROLINK_REQUIRE_ENCRYPTED_CREDENTIALS=true`，SQLite 全新库）：

| 动作 | 结果 |
| --- | --- |
| 明文创建超管 / 明文登录 / 明文改密 | 400 `encrypted_credential_required` |
| 密文创建超管 / 密文登录 / 密文改密 | 201 / 204 / 200 |
| 只发 `username`（凭据整体缺省） | 400 `invalid request payload`（handler 的必填，不是加密要求） |
| 坏密文 | 400 `credential_decrypt_failed` |
| 关掉开关后同一批动作（复用同一个库） | 明文全部恢复正常（204 / 200） |
| `tools/apismoke` 对着强制模式实例 | 打印"改用密文重试登录"，`PASS 登录`、`PASS 会话可用` |

运维注意：

- **升级顺序**：先发布本版本（前端产物随二进制走，浏览器里的旧标签页仍是旧的），确认没有旧页面在用、
  也没有自行调用 API 的脚本，再打开开关。开关是进程级环境变量，改它等于重启一次。
- 打开后，任何仍发明文的第三方脚本（自建自动化、旧的 apismoke 二进制）会 400；`tools/apismoke`
  当前版本已自带回退，不需要额外参数。
- 强制模式**不替代 TLS**：它挡的是"明文凭据进日志/被抓包看内容"，挡不住中间人重放合法密文与篡改响应
  （见 §6）。P0 仍是必做项。
- 排查时若看到 `encrypted_credential_required`，先去查客户端的加密是否真的走通（`/api/v1/transport-key`
  是否可达、多副本私钥是否一致），不要先去关开关。
