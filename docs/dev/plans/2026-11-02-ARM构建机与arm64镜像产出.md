# ARM（aarch64）构建机与 arm64 镜像产出

日期：2026-11-02
状态：已实现

## 1. 背景与结论

仓库原有的两条出镜像路径都只产 amd64：`make image`（容器内构建，基座与构建镜像都是 amd64）
和 `make image-binary`（本机编译 + `Dockerfile.binary`，本机是 x86_64）。`make cross-compile`
虽然能出 `bin/aerolink-arm64`，但它是 `-tags duckdb_cli` 的纯 Go 产物，**不含进程内 DuckDB
引擎**，用它建镜像会让 parquet 审计检索失效（`Dockerfile.binary` 的头注释已经写明这点）。

所以 arm64 只能**原生编译**：用一台 ARM 机器跑 `pnpm build` + `CGO_ENABLED=1 go build`，再用
`Dockerfile.binary` 打镜像。本轮落地的构建机是 4C/15G/50G 磁盘的公有云 ARM 机器，产物
`swr.../devops/aerolink:v1.0.2-arm64`（push 后回拉校验 `arch=arm64`，容器内起服务 +
`go test ./pkg/audit/` 全过）。

**该构建机已于同日删除**（一次性验证机）。已推入 SWR 的两个 arm64 镜像不依赖它，在开发机上只读
manifest 复核仍在（见 §6）；重架按 `scripts/provision-arm64-builder.sh` 一键走，不必重新踩坑。

## 2. 为什么能成：三条硬前提

| 前提 | 构建机 | 运行基座 | 不满足会怎样 |
| --- | --- | --- | --- |
| glibc 版本线 | TencentOS Server 4 = 2.38 | openEuler 24.03-lts-sp4 = 2.38 | 构建机高于基座 → 容器里 `GLIBC_2.xx not found` |
| libstdc++ | gcc/g++ 12.3.1（libstdc++.so.6） | openEuler 自带 libstdc++ | CGO 产物 NEEDED `libstdc++.so.6`，musl 基座直接跑不起来 |
| DuckDB 静态库 | vendor 里有 `duckdb-go-bindings/lib/linux-arm64/*.a` | — | 缺这份库就没法在 arm64 上开 CGO 链出引擎 |

构建机与基座的 glibc **恰好同线**（都是 2.38），这是当初选 openEuler 24.03 作基座时留下的
好处：换 ARM 机器不需要改成静态链接。核对方式（比翻符号版本表更直接）：

```bash
file aerolink                                              # ELF 64-bit LSB executable, ARM aarch64
docker run --rm --platform linux/arm64 -v ./aerolink:/a:ro <基座 arm64> /a --help
```

第二条能打印 usage，就说明动态链接与 C++ 运行时都解开了。

## 3. 构建机 provisioning（一次性）

下面的步骤已经汇总成可执行脚本 **`scripts/provision-arm64-builder.sh`**（在新 ARM 机上以 root
直接跑）：脚本本身没整份实跑过，但其中每一条命令都是本轮在真实机器上跑通过的，二者差别只在「没有
逐步人工核对输出」。

## 4. 卡在基座镜像：SWR 里只有 amd64 的 openEuler

`Dockerfile.binary` 写死的基座 `gzwxh/docker.io/openeuler/openeuler:24.03-lts-sp4` 在 SWR 里是
**单架构 amd64 manifest**（`docker pull --platform linux/arm64` 会回落到 amd64，inspect 出
`arch=amd64`），拿不到 arm64 层。构建机又拉不到 `docker.io` / `registry-1.docker.io` /
`hub.openeuler.openatom.cn`（全部 TCP 超时），只有镜像加速站 `docker.m.daocloud.io` 可用。

处置：把加速站上的 arm64 基座转推一份进公司 SWR，tag 加 `-arm64` 后缀。

**为什么不原地覆盖同名 tag**：SWR 对 manifest list 的支持不行 —— 正因为这样，本仓库的镜像构建
必须带 `--provenance=false --sbom=false`（`Makefile` 里那段注释）。所以「同一个 tag 两个架构」
这条路在目标仓库上不可依赖，只能拆 tag；不覆盖也顺带保住了 amd64 那条构建路径的既有引用。

```bash
docker pull --platform linux/arm64 docker.m.daocloud.io/openeuler/openeuler:24.03-lts-sp4
docker tag  docker.m.daocloud.io/openeuler/openeuler:24.03-lts-sp4 \
            swr.cn-south-1.myhuaweicloud.com/gzwxh/docker.io/openeuler/openeuler:24.03-lts-sp4-arm64
docker push swr.cn-south-1.myhuaweicloud.com/gzwxh/docker.io/openeuler/openeuler:24.03-lts-sp4-arm64
```

为让基座可覆盖，本轮一度把 `Dockerfile.binary` 参数化了（`ARG RUNTIME_IMAGE` + `ARG DUCKDB_BIN`、
零 RUN 化、数字 USER）；后来评估出**改动面太大**，已经回退：`Dockerfile.binary` 保持原样（只服务
CGO + 内嵌 SDK 的本机产物），本地交叉构那条单独拆到 **`Dockerfile.arm`**（见 §9）。
回退后的实际影响：原生 ARM 机器上直接 `make push-binary GOARCH=arm64` 就能跑（基座默认解析到
SWR 那个 amd64 tag）—— 本轮的 v1.0.2-arm64 SDK 镜像就是这么出的：ARM 机器自带 qemu-user-static，
`RUN` 步能被模拟，所以基座层是 amd64 不妨碍产出可用的 arm64 镜像（本项目只依赖 glibc/libstdc++）。
想要干净基座，就手工 `docker build -f Dockerfile.binary --build-arg …`，或先把 arm64 基座推成同名 tag（需仓库支持 manifest list）。

## 5. 日常构建命令（可重复）

```bash
# 构建机上
. /etc/profile.d/aerolink-build.sh
cd /root/aerolink
bash scripts/get-version.sh        # 版本号口径：当前工作区 v1.0.2-36-g6bfc0e4 → v1.0.3-p36-6bfc0e4

make image-binary GOARCH=arm64 \
  RUNTIME_IMAGE=swr.cn-south-1.myhuaweicloud.com/gzwxh/docker.io/openeuler/openeuler:24.03-lts-sp4-arm64 \
  IMAGE=swr.cn-south-1.myhuaweicloud.com/gzwxh/devops/aerolink:<tag>
docker push swr.cn-south-1.myhuaweicloud.com/gzwxh/devops/aerolink:<tag>
```

`image-binary` 依赖 `build`（前端 + CGO 后端），一次约 4 分钟（4 核：前端 ~150s，后端 ~180s，
其中 DuckDB 的 C++ 目标文件在 Go 构建缓存里复用）。产物基线：二进制 218M，镜像 ~286MB。

**tag 里带 `-arm64`，不带就等于 amd64**：两个架构是两个独立 tag，不是同一 tag 的 manifest list
（理由见上一节）。部署侧要显式选 arm64 那个 tag：Helm 用 `--set image.tag=v1.0.2-arm64`，
或改 `charts/aerolink/values.yaml` 的 `image.tag`。

版本号与 tag 要一致：`make image-binary` 里的 `VERSION` 取 `Makefile` 默认值（当前 `v1.0.2`），
它会烧进二进制并由 `/api/v1/version` 报出；tag 若写成 `v1.0.3-arm64` 就会出现「镜像名 v1.0.3、
界面 v1.0.2」。要发新版本时同步 `make image-binary VERSION=vX.Y.Z ... IMAGE=...:vX.Y.Z-arm64`。

## 7. 构建机安全与运维

本轮的机器是一次性验证机，**已在同日删除**。下面这些是当时没做完的收尾，机器删了不等于它们
自动生效（公钥与长期访问密钥在云端，不在那台机器上）：

- **必须轮换 SWR 的长期访问密钥**：本轮用的是子账号长期 AK/SK（`cn-south-1@HPUAEJI…`），它在
  对话、构建机 `/root/.docker/config.json` 里都明文出现过（前者已删机但对话记录在）。密钥只能
  在华为云控制台解绑/轮换才能收回，删机本身不使其失效。
- **从各云主机 `authorized_keys` 里移除开发机的 `id_ed25519` 公钥**（本轮 `ssh-copy-id` 只推了
  这一台，已随机器消失；开发机私钥未外流）。
- 以后重架时不要再走长期 AK：改用华为云 SWR **临时登录指令**（小时级失效），并把安全组限到
  运维出口 IP、sshd 关 `PasswordAuthentication`。
- **磁盘**：50G 根分区，一次构建占 11~12G（docker 镜像与构建缓存）。`image-binary` 每次会
  `rm -rf dist/`，但 Go / pnpm 缓存只增不减；建议加 `docker system prune -f` 与
  `go clean -cache` 的定期清理，或挂一块数据盘放 `/root/go`、`/var/lib/docker`。
- 代码只在构建机上留一份工作副本（rsync 覆盖式同步，不建 git 远端），改代码仍以内网开发机为准；
  删机前没做工作区清单留档，不过镜像可用 digest（`sha256:c34a63bd81e1…`）反查，代码以 git 为准。
- 删机**不影响已推产物**：arm64 应用镜像与 arm64 基座都在 SWR 里，部署侧继续用 `-arm64` tag 即可。

## 9. 本地（x86 / WSL2）交叉出 arm64 镜像

同日补上，入口是 `make build-arm` / `make push-arm`，镜像文件是 **`Dockerfile.arm`**（与
`Dockerfile.binary` 分开）。它既不依赖 ARM 机器，也不依赖 QEMU。

### 9.1 为什么能绕开模拟

两个环节各自成立，才凑成「本地可交」：

| 环节 | 原本卡在哪 | 本方案的解法 |
| --- | --- | --- |
| 后端编译 | CGO + DuckDB SDK 要 arm64 的 C/C++ 工具链（本机 `aarch64-*-g++` 一个都没有） | 换 `-tags duckdb_cli`（纯 Go），`CGO_ENABLED=0 GOARCH=arm64` 在宿主机直接交叉 |
| 镜像组装 | `Dockerfile.binary` 里的 `RUN`（写 passwd/group + chown）要在 arm64 里执行 `/bin/sh` | `Dockerfile.arm` **零 RUN**：目录与属主全用 `COPY --chown` 造，登录用户用数字 `USER 65532:65532`（不需要 passwd 条目） |

本机确实没有用户态模拟（WSL2 内核未注册 qemu binfmt，`docker run --platform linux/arm64 hello-world`
直接 `exec format error`；dnf 里也没 `qemu-user`），所以「在容器里编 arm64」这条路在本地走不通，
必须把两个环节都择到宿主机 + 零 RUN 上。

### 9.2 两个靠实测才现形的坑

- **`/home/aerolink` 本身必须是 65532 属主**。sqlite 的默认 DSN 是**相对路径** `dev.db`
  （`pkg/common` 的 `DBDSN`），落在 WORKDIR 里。只靠 `WORKDIR` + `COPY --chown` 的话，
  `/home/aerolink` 是 root:root 755（COPY 只把它**创建的目标子目录**给属主，不给中间层目录），
  非 root 启动直接 panic：`failed to connect database: unable to open database file: out of memory (14)`。
  解法：在 `$BUILDPLATFORM` 阶段 mkdir 出 `/stage/home/aerolink/data/archive`，再用
  `COPY --from=… --chown=65532:65532 /stage/home /home` 把家目录**这一层本身**带成 65532。
- **全局 ARG 必须写在第一个 FROM 之前**。夹在两个 FROM 之间的 `ARG RUNTIME_IMAGE` 会被前一个
  阶段结束作用域，`FROM ${RUNTIME_IMAGE}` 展开成空值，报
  `base name (${RUNTIME_IMAGE}) should not be blank`；而在 FROM **之前**重复声明同名 ARG 也一样空。

### 9.3 基座兼容性核对（换 DUCKDB_VERSION 前必跑）

镜像里的 `duckdb` 是官方发布件，它自己的 glibc / libstdc++ 要求必须被基座覆盖。不靠模拟的核对方法：

```bash
# 1) duckdb 要什么
readelf -d duckdb | grep NEEDED                                    # libstdc++.so.6 / libgcc_s / libc …
strings -a duckdb | grep -oE "GLIBC_[0-9.]+" | sort -V | tail      # 实测 v2.0.0：GLIBC_2.25 为止
strings -a duckdb | grep -oE "GLIBCXX_3\.4\.[0-9]+" | sort -V | tail # 实测 v2.0.0：GLIBCXX_3.4.22
strings -a duckdb | grep -oE "CXXABI_1\.3\.[0-9]+" | sort -V | tail  # 实测 v2.0.0：CXXABI_1.3.11
# 2) 基座给什么（openEuler amd64 基座实测；arm64 同一份包，libstdc++.so.6.0.30 = GCC 12.3 → 到 3.4.30）
docker run --rm <基座> sh -c 'ldd --version | head -1; ls /usr/lib64/libstdc++.so.6*'
# 3) 能跑证据：同版本发布的 x86 duckdb 在基座容器里 select version()
docker run --rm -v ./duckdb-amd64:/duckdb:ro <基座> /duckdb -c "select version();"
```

另外纯 Go（CLI 驱动）下 `CGO_ENABLED=0 go test -tags duckdb_cli ./pkg/audit/` 已在本机跑过（ok 10.3s），
SDK 写的 parquet 由 CLI 读这条链路不依赖 CGO。

### 9.4 实测计时（8 核 / 7G 的 WSL2）

| 阶段 | 冷构 | 热构（命中缓存） |
| --- | --- | --- |
| 前端 `pnpm run build` | — | 4.2 s |
| 后端交叉编译（arm64） | 85 s（首次，实测 178M 静态产物） | 4.7 s（Go 构建缓存） |
| 镜像组装（Dockerfile.arm） | 十几秒（上传 141M 二进制 + 74M duckdb） | 0.6 s（BuildKit 层缓存） |
| `docker push` 到 SWR | ~1 分钟（上传量看仓库侧已有层） | 4.6 s（层全复用） |
| 整条 `make build-arm` | 约 2 分钟 | **19 s** |

对比：原生 ARM 机器（4C/15G）上 `make image-binary` 约 4 分钟，但带内嵌引擎。

提速就集中在三处缓存，都默认生效，别随手清理：

1. **Go 构建缓存**（`go env GOCACHE`）——交叉编译从 85s 降到 5s；只有改依赖/改 flags 才会重偏。
2. **BuildKit 层缓存**——产物内容没变时 `COPY` 直接复用（0.6s），所以重跑只重做变化部分。
3. **duckdb 按架构+版本落盘**（`dist-arm/duckdb-<arch>-<ver>`）——已存在就不重复下载 21MB。

反例（不值得做）：想靠 buildx + QEMU 在本地跑容器内构建 —— 一来本机没 binfmt，二来即使补上，
DuckDB 的 C++ 在模拟层编译在 8 核/7G 上是几十分量级、链接阶段还有 OOM 风险。

### 9.5 产物基线与已知限制

- `swr.../devops/aerolink:v1.0.2-arm64`（纯 Go 驱动）：digest `sha256:afee4a90de0c…`，`arch=arm64`，
  `user=65532:65532`。这个 tag 原先是原生 ARM 构的 SDK 版（digest `sha256:c34a63bd81e1…`），
  **已被覆盖**；两个驱动功能等价，但不是同一份二进制，回滚要重跑原生 ARM 构。
- amd64 等价物本地跑过：容器起来、`/api/v1/version` 与首页 200、`/usr/local/bin/duckdb` 可执行。
- arm64 成品**本地跑不起**（无模拟），上线前请在真 ARM 机器/K8s 节点上至少跑一次
  `/api/v1/version` 与一条审计归档检索（验证镜像里的 duckdb 能 exec）。
