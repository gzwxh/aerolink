# 集群改名保留权限绑定

## 背景与问题

「系统设置 → 集群 → 编辑集群」里改了集群名（名称 `*`）之后，原本通过权限绑定组拿到
授权的用户会**静默失去该集群的全部权限**：集群列表里还看得到它，进去全是 403。

## 根因（结论：和权限绑定直接相关）

集群名是权限数据的事实外键，但这几张表没有 `cluster_id`，只存集群名字符串：

- `binding_groups.cluster`（`pkg/model/binding_group.go`）
- `binding_group_namespaces.cluster`（同上，唯一性按集群判定，冗余了同一份名字）

授权判定拿请求里的当前集群名去比对：`pkg/rbac/binding_group.go` 的
`bindingGroupsCache.projects[projectID] != cluster` / `byNamespace[cluster+"/"+namespace]`。
改名只更新了 `clusters.name`（`model.UpdateCluster`），上面两张表仍留在旧名字上，于是：

1. 组自身的 `Detached` 仍是 `false`，但已经指向一个不存在的集群，判定永远不命中；
2. 权限绑定页按 `?cluster=<当前集群名>` 取数（`pkg/bindinggroups/handler.go` 的
   `ListBindingGroups`），列表里直接看不到这些组，管理员也发现不了它们还"挂着"；
3. 界面上只有 **detached（集群已删除、配置被保留）** 的组提供「重新绑定」入口，
   本场景的组不是 detached，没有任何恢复路径 —— 只能人工改库。

超级管理员不受影响：他的 `admin` 角色是直接分配（`clusters: ["*"]`），不走绑定组，
所以现场表现通常是「管理员看着一切正常，普通用户全掉权限」。

同类的、本次**没有一起改**的按名引用（历史数据/非授权）：

- `scheduled_tasks.cluster_name`（HelmRelease 自动升级计划；改名后计划不再触发）
- `resource_history.cluster_name`、审计日志的 `cluster_name`（历史记录，本是快照语义）

## 方案

1. `pkg/model/cluster.go` 新增 `RenameCluster(cluster, newName, updates)`：
   **一个事务**里完成
   - 占用检查：目标名字已被别的集群占用，或已有同名集群保留下来的权限绑定组 → 返回
     `ErrClusterNameTaken`（`(cluster, name)` 唯一索引也挡着，但需要显式 409 而不是 500）；
   - 迁移 `binding_groups.cluster` 与 `binding_group_namespaces.cluster` 到新名字；
   - 落其余字段更新与 `clusters.name`。
   任一步失败整笔回滚，不会出现「集群改了名、权限还在旧名下」的半套状态。
2. `ClusterManager.UpdateCluster` 改名走 `RenameCluster`，冲突回 `409`；改名成功后
   `rbac.TriggerSync()` 重建授权缓存（否则后台一分钟一次的同步之前的请求仍按旧名判定）。
   非改名的更新路径与 `model.UpdateCluster` 保持原样。
3. 前端（`ui/src/components/settings/cluster-management.tsx`）：更新成功后同时失效
   `['clusters']`（5 分钟缓存，顶栏/切换器/命名空间映射都读它）与 `['binding-groups']`
   （权限绑定页按集群名取数）；`onError` 不再静默，把 409 的原因提示出来。

## 不变的部分

- `clusters.slug` 仍创建时固化，改名不重算（已分享链接优先，见
  `2026-10-15-集群信息进入浏览器地址栏.md`）。
- 不做库结构变更，无升级 SQL。
- 集群作用域 / 命名空间作用域、RBAC 判定口径、AI 工具授权路径都不动。

## 测试

`pkg/cluster/cluster_handler_test.go` 新增
`TestUpdateClusterRenameCarriesBindingGroups`：改名前后的绑定组与命名空间归属跟随新名字；
目标名被其它集群占用、被保留的绑定组占用时返回 409 且集群名与权限数据都不动。
