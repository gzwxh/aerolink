# 方案：页面「刷新」重新取全页数据

- 状态：**已实现**
- 触发：用户反馈「Pod 已经删除了，点页面上的刷新按钮列表还是旧的，只有浏览器整页重载才更新」，
  确认口径为：刷新按钮 = **重新取这一页展示的全部数据**（而不是整页 reload）。

## 1. 问题

详情页的「刷新」按钮语义不完整。这一页的数据分三类，原来只有前两类被覆盖：

| 数据                                    | 来源                                                 | 点「刷新」是否更新（改前）                   |
| --------------------------------------- | ---------------------------------------------------- | -------------------------------------------- |
| 主资源（Deployment 本体、副本数、状态） | `useResource`（react-query）                         | ✅ 页面传的 `onRefresh`                      |
| 事件、相关资源、监控、Endpoints         | 各自独立的 react-query 查询                          | ✅ 外壳 `refetchQueries({ type: 'active' })` |
| **Pods 列表 / Pod 数**                  | **`useResourcesWatch`（SSE，数据在组件本地 state）** | ❌ **碰不到**                                |

`useResourcesWatch` 的列表由 SSE 事件（`added`/`modified`/`deleted`/`metrics`）维护在
`useState` 里，**不在 react-query 缓存中**，所以 `refetchQueries` 对它无效；要更新只能调用
它自己的 `refetch`（断开重连 + 重新取快照）。

改前的补救办法是「让每个详情页在 `onRefresh` 里自己带上 `refetchPods()`」：6 个用了 watch 的
详情页里 4 个漏了（`job-detail` / `service-detail` 接了，`deployment` / `statefulset` /
`daemonset` / `helmrelease` 没接），并且只能靠一条源码级断言（扫 `refetchPods()` 字样）兜住。
**按钮行为依赖页面作者的记忆，本身就是设计缺陷的信号**——正确性应当是结构性保证。

另外，半开连接（TCP 还在、服务端不再推事件）时浏览器不会触发 `onerror`，hook 也不会自动重连，
页面会一直停在旧快照上。这正是手动刷新按钮不可替代的地方：它必须**强制重连 + 重取快照**。

## 2. 目标

- 点「刷新」后，这一页展示的任何一块数据都不再是旧的（主资源、同页查询、流式连接、派生值）。
- 范围只限**当前挂载的页面**：不去刷新其它页面/路由的数据（`type: 'active'` 已经是这个口径）。
- 不动 UI 状态：正在编辑的 YAML 草稿、选中的 tab、滚动与折叠状态全部保留——这是「按钮」与
  「浏览器 F5」的区别，也是不做整页 reload 的原因（reload 还会重下 JS/CSS）。
- 新加的数据源（以后再多一条 watch / 轮询）只要走既有 hook 就自动被覆盖，页面不必再记任何事。

## 3. 做法：页面级刷新信号

新增 `ui/src/contexts/page-refresh-context.tsx`：

- 值只有两项：`epoch`（递增代数，初值 0）与 `refresh()`（bump 一次）。
- `PageRefreshProvider` 挂在**应用根部**（`App.tsx` 的 `AppProviders`），不是挂在页面外壳里。
  原因：页面组件自己在 shell **之外**调用 `useResourcesWatch`（hook 调用点在页面组件里），
  外壳内部的 Provider 覆盖不到它。
- 缺省值是 `{ epoch: 0, refresh: () => {} }`：没有 Provider 的地方（单测里单独渲染、
  外壳之外的组件）退化为「没有刷新信号」而不是抛错。

订阅侧：

- `useResourcesWatch` 读 `epoch`，**变化时**调用自己的 `refetch({ immediate: true })`。
  首次挂载不触发（记住初始代数再比较），`refetch` 身份变化（`labelSelector` 变了等）也不触发。
- `ResourceDetailShell.handleRefresh` 在原有动作之外 bump 一次：
  `onRefresh()` + `refetchQueries({ type: 'active' })` + `refresh()`。

选择「递增代数」而不是事件回调 / 订阅表：单向数据流、幂等，订阅者自己比较新旧值即可，
不需要关心谁先挂载、也不需要清理订阅（订阅的是 React 自己的 context）。

### 3.1 `refetch` 增加 `immediate`

原 `refetch()` 走指数退避（1s → 30s 封顶），那是给**自动重连**抗抖动用的。用户显式点刷新是
一次性动作，不该等退避（连着失败几次后点一次要等 30s）。因此 `refetch({ immediate: true })`
重置退避计数并立刻重连；自动路径的行为不变。降级轮询状态下保持原逻辑（直接 `pollList()`，
不抢 SSE）。

## 4. 接线收敛

撤掉上一轮给 `deployment` / `statefulset` / `daemonset` / `helmrelease` 四个详情页手工加的
`refetchPods()`，页面回到 `onRefresh={refetch}`：主资源之外的查询与流式数据都由外壳统一覆盖，
页面不再需要知道这一页有哪些数据源。

`job-detail` / `service-detail` 里原有的显式 `refetchPods()` 保留（`service-detail` 的
`handleRefresh` 还被保存 YAML 的路径复用）：它们与刷新信号会各触发一次，净效果仍是那次
「立即重连」——刷新信号走 `immediate`（0ms）会覆盖页面那次带退避的定时器，行为正确，
只是多一次调用。这次不去动这两处既有代码，避免扩大改动范围。

同时删掉上一轮临时加的 `ui/src/pages/detail-refresh-wiring.test.ts`（源码级断言）——约定已经
变成机制，不再需要靠扫源码来保证；回归改由 `lib/api/core.test.ts` 覆盖刷新信号本身。

## 5. 不改的部分

- 列表页的刷新按钮：`use-resource-table-data` 已经把 `refetch` 接到 `watch.refetch`，行为不变
  （列表页不 bump 信号，生命周期与详情页无关）。
- 后端：不做任何改动。
- 不引入 `window.location.reload()`：丢草稿与 UI 状态、重下资源，而且是把问题绕过去而不是修掉。

## 6. 验证

- `pnpm --dir ui exec vitest run src/lib/api/core.test.ts`
  （新增：刷新代数变化时重建 EventSource、并立刻重取；`immediate` 不吃退避）。
- `pnpm --dir ui exec vitest run`（全量，含删掉源码断言后仍全绿）。
- `pnpm --dir ui exec tsc --noEmit -p tsconfig.app.json`。
- 手工：详情页删掉一个 Pod（或用 `kubectl delete pod`）→ 点「刷新」，Pods 卡片在 1 秒内更新，
  且 YAML 标签页的未保存草稿不被冲掉。
