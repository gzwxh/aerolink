# 登录日志双维度 IP 记录（公网出口 + 原始来源）

## 背景

部署在公司内网入口时，请求经过 `内网客户端 → 公司出口 NAT → SLB/nginx → AeroLink`
多级代理。`c.ClientIP()`（Gin）只返回 X-Forwarded-For 链中「从右往左第一个非信任代理」
的 IP：

- 直连公网时 = 公网 IP，正常；
- 内网用户经 NAT 时 = **公司出口公网 IP**，而其内网原始地址（如 `10.1.2.100`）被丢弃。

结果：登录日志只能看到一个出口 IP（同公司大量人员共用），既无法定位到具体内网机器，
也看不出是哪个公网出口进来的。需求是**同时记录两个维度**：

| 字段 | 含义 | 用途 |
|---|---|---|
| `ip` | `ClientIP()` 返回值（公网出口 / 直连 IP） | 地理定位、异地登录判定 |
| `source_ip` | X-Forwarded-For 最左边的原始客户端 IP | 内网溯源到具体机器 |

## 实现

### 提取规则

`pkg/utils/ip.go` 新增 `ExtractSourceIP(xForwardedFor, remoteAddr)`：

1. `X-Forwarded-For` 非空 → 取第一个非空 IP（标准链最左边是原始客户端）；
2. 链为空 → 回退 `RemoteAddr` 去掉端口（直连场景即真实客户端）。

`ip` 继续用 `c.ClientIP()`，不改既有语义（含 IP 黑名单、失败锁定、异地判定）。

### 改动面

- `pkg/model/notification.go`：`LoginRecord` 新增 `SourceIP`（`source_ip varchar(64)`）；
  `RecordLogin` / `RecordLoginFailure` 增加 `sourceIP` 参数。
- `pkg/auth/login_handler.go`、`pkg/notification/triggers.go`：调用点同时传入两个 IP；
  异地登录通知模板新增 `{{sourceIp}}` 占位符（`pkg/notification/handler.go` 同步登记）。
- 归档/导出/检索：
  - parquet `loginRecordRow` 新增 `source_ip` 列；
  - ES 文档新增 `source_ip`；
  - 本地 CSV 与归档 CSV 均新增 `sourceIp` 列，表头保持一致；
  - 列表搜索（库路径与归档路径）从「username / ip」扩展到「username / ip / source_ip」。
- 前端：`LoginRecord` 类型加 `sourceIp`；登录日志表格新增「来源 IP」列（i18n：
  `common.fields.sourceIp`），只读文本，不参与筛选。
- syslog / stdout 通道**不改**：其 key=value 输出是既有字节级契约，`source_ip` 只进
  库、归档与界面。

### 旧归档兼容

`source_ip` 插在 parquet 行的中间列位；旧归档文件没有该列。DuckDB 检索语句加上
`union_by_name=true`，按列名合并 schema、缺失列补 NULL——否则默认按首文件 schema
对齐会串列（`user_agent`/`result` 错位）。回归测试
`TestDuckDBSDKBackendMixesLegacyLoginArchivesWithoutSourceIP` 覆盖新旧文件混查。

## 库结构变更（升级必读）

`login_records` 新增一列，需人工执行（生产库应用账号通常不是表 owner，AutoMigrate
加列会被 PostgreSQL 拒绝，只告警不阻断启动）：

```sql
-- SQLite
ALTER TABLE login_records ADD COLUMN source_ip varchar(64);

-- MySQL 5.7 / 8.x
ALTER TABLE login_records ADD COLUMN source_ip VARCHAR(64) NULL;

-- PostgreSQL 12+
ALTER TABLE login_records ADD COLUMN IF NOT EXISTS source_ip VARCHAR(64);
```

执行账号：PostgreSQL 需表 owner；MySQL / SQLite 需 ALTER 权限。升级后核对
`information_schema.columns`（或 `PRAGMA table_info`）里 `login_records.source_ip` 存在。

已执行（2026-11-26）：

- 本地开发库 `dev.db`（SQLite）：列已存在，并清除了改名过程中的临时列 `egress_ip`；
- 云上实例（134.175.219.203 的 aerolink 容器 → MySQL 8.0.30 @ 10.32.2.244，库 `aerolink`）：
  已执行 `ALTER TABLE login_records ADD COLUMN source_ip VARCHAR(64) NULL`，102 行历史数据保留。
- node1 验收实例（10.100.117.8，`/opt/aerolink/dev.db`，SQLite）：已执行同样的 ADD COLUMN，3 行保留；
- 开发 K8s（10.10.11.99 的 `aerolink` 命名空间 → PostgreSQL 12.12 @ 10.10.11.111，库 `aerolink`）：
  应用账号非表 owner（SQLSTATE 42501），已由 `postgres` 超级用户执行 ADD COLUMN，67 行保留。

历史行该列为 NULL，界面显示 `-`；新登录开始双向记录。

## 前置条件

`X-Forwarded-For` 只有直连对端在 `TRUSTED_PROXIES` 内时才被采信（Gin 行为）。入口
是 nginx/SLB 时，`TRUSTED_PROXIES` 必须收窄为真实代理地址或网段，否则 SourceIP
不可信；直连部署必须设为 `none`。

## 验证

本地实测（`TRUSTED_PROXIES=127.0.0.0/8`，curl 模拟多级代理）：

| 模拟链路 | X-Forwarded-For | ip | source_ip |
|---|---|---|---|
| 内网 → 公司 NAT | `10.1.2.100, 203.0.113.50` | `203.0.113.50` | `10.1.2.100` |
| 内网 → NAT → SLB | `192.168.10.77, 203.0.113.51, 218.201.197.186` | `218.201.197.186` | `192.168.10.77` |
| 公网直连 | `198.51.100.10` | `198.51.100.10` | `198.51.100.10` |

`go test ./pkg/audit ./pkg/model ./pkg/utils ./pkg/auth ./pkg/notification` 全绿；
